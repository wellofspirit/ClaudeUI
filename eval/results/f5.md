# Bundle-split analysis: `[5/8] web build` chunk size warning

**Date:** 2026-08-13 · **Branch:** `pre-release`

## Question

Vite warns that some chunks exceed 500 kB after minification in the web build step.
Does it make sense to split bundles?

## TL;DR

Further bundle splitting is **low value** — the build already splits where it matters.
The real findings are in `remote-server.ts`: static assets for the remote web client are
served with **no caching and no compression**. Fixing those dwarfs any chunking win.
After that, a single vendor `manualChunks` split becomes a modest cross-release
cache optimization; the warning itself should just be silenced with an honest
`chunkSizeWarningLimit`.

## Context: which build this is

- `[5/8] web build` = `vite.web.config.ts` → `out/web` — the **remote browser client**
  served over tailscale (ADR-042), not the Electron renderer.
- The Electron renderer is a separate build (`electron.vite.config.ts` → `out/renderer`)
  loaded from disk, where chunk size is irrelevant (no network; one-time parse cost).

## Current state of the web build

65 JS chunks; all mermaid diagram renderers are already lazy-loaded. Only two chunks
exceed the 500 kB limit:

| Chunk | Raw | Gzipped | Notes |
|---|---|---|---|
| `App-*.js` | 2.1 MB | 551 kB | entire renderer app, lazy-loaded after auth |
| `cynefin-*.js` | 688 kB | 154 kB | mermaid-internal chunk, already lazy — not actionable |

Load flow is already right (`src/web/main.tsx`):

1. Small entry (~75 kB gz) renders the password login immediately.
2. `@renderer/App` is dynamically imported only after connection + `sync-full` snapshot.

So the 2.1 MB chunk does not block time-to-login, and after login essentially all of it
is needed (sidebar, chat, stores, xterm). Splitting `App` into route/feature chunks would
mostly add waterfall hops.

## The real issues: serving path, not chunking

`serveStatic` (`src/main/services/remote-server.ts:1472`) streams files with security
headers only:

1. **No `Cache-Control`, no `Last-Modified`/`ETag`** — hashed immutable assets get
   effectively zero browser caching. Every visit re-downloads ~3 MB.
2. **No compression** — no `Accept-Encoding` handling; wire cost is the raw 2.1 MB
   instead of 551 kB. On a DERP-relayed tailscale connection (mobile/off-network,
   often single-digit Mbps) that's ~2 s vs ~10 s first paint after login.

Fixes (small, ~4× first-load and ~100% repeat-load improvement):

- `/assets/*` (content-hashed): `Cache-Control: public, max-age=31536000, immutable`;
  `index.html`: `no-cache`.
- Precompress at build time (vite compression plugin emitting `.gz`/`.br` siblings) and
  serve them from `serveStatic` when `Accept-Encoding` allows — simpler and cheaper than
  on-the-fly compression in the main process.

## Vendor split — only worth it after caching exists

Once immutable caching is in place, one `manualChunks` split (react, xterm, mermaid core,
katex vs app code) means a ClaudeUI release only invalidates the app chunk, not the full
~551 kB. Genuine but modest win given frequent releases. Without cache headers it is
worthless — everything re-downloads regardless.

## Recommendation

1. **Don't restructure bundles now.** Set `build.chunkSizeWarningLimit` in
   `vite.web.config.ts` (~800 kB with `App` as a known exception, or 2200 to silence).
2. **Do the caching + precompression fix in `serveStatic`** — the real perf item behind
   this warning. Keep the traversal-safe path handling intact; add tests.
3. **Revisit vendor `manualChunks` only after #2**, as a cross-release cache-hit
   optimization.
