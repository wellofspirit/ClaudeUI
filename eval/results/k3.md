# Bundle Splitting Analysis — k3

**Question:** The build warns about chunks >500 kB after minification (`[5/8] web build`).
Does it make sense to split bundles?

**Short answer:** For the Electron renderer — no, splitting is pointless. For the web
client (where the warning actually comes from) — one targeted split (mermaid) is worth
it, but the bigger wire wins are two server-side changes (compression + cache headers),
not chunking.

## Where the warning comes from

Step `[5/8] web build` runs `vite build --config vite.web.config.ts` → `out/web`, the
remote-access browser client served by `src/main/services/remote-server.ts` from the
desktop app (LAN / Tailscale / cloudflared tunnel).

Current chunk layout (`out/web`, total 5.4 MB):

| Chunk | Size (min) | Gzipped | Loaded when |
|---|---|---|---|
| `index` (auth shell) | 231 KB | 75 KB | immediately |
| `App` (shared renderer) | **2.0 MB** | 548 KB | after WS connect + first sync-full |
| mermaid sub-chunks (cynefin, cytoscape, katex, diagram types) | 40–670 KB each | — | already lazy, on first diagram render |

The layering is already good: small auth shell first (`src/web/main.tsx`), app code
lazy-imported after hydration (`import('@renderer/App')`), mermaid's per-diagram chunks
pay-as-you-go via mermaid's internal dynamic imports.

The Electron renderer (`out/renderer`, 3.9 MB entry) loads from local disk and parses
once at startup (~100 ms). Splitting there is pure complexity — don't.

## The whale: mermaid core

`src/renderer/src/components/chat/MermaidDiagram.tsx` does a static
`import mermaid from 'mermaid'`. The per-diagram chunks are lazy, but mermaid *core*
(dagre/d3 graph, est. ~half the 2.0 MB `App` chunk based on mermaid's dist layout) is
in the critical path even though most chat sessions never render a diagram.

## Serving-side findings (`remote-server.ts`)

- `serveStatic` (line 1472) pipes files raw — **no `Content-Encoding`** (no
  gzip/brotli). 2.0 MB truly travels as 2.0 MB.
- `/assets/*` responses carry **no `Cache-Control`** at all, so repeat visits refetch
  everything (heuristic caching on a freshly-built bundle ≈ nothing).
- Static assets are unauthenticated **by design**: the WS token rides the URL fragment
  (never sent in the HTTP request), and data flows over the authenticated WS. Serving
  the JS to anyone is safe — which also makes pre-auth prefetching safe.
- Cloudflared's edge already compresses tunnel traffic, so the missing-compression cost
  mainly hits LAN / Tailscale-direct connections.

## Why blanket `manualChunks` splitting is rejected

- Doesn't reduce total bytes — it optimizes *cache granularity across frequent
  deploys*, irrelevant for a client version-locked to the desktop app that serves it.
- More chunks = more request round-trips on the plain Node HTTP/1.1 server. Over a
  cloudflared tunnel on cellular, a waterfall of 8 chunks can be *slower* than one
  2 MB file.
- `chunkSizeWarningLimit`'s 500 kB default is calibrated for public websites, not this
  point-to-point topology.

## Recommendations, in order

1. **Compress in `serveStatic`** — biggest win, zero renderer changes. Precompress at
   build time (`.br`/`.gz` siblings) and serve with the right `Content-Encoding`:
   2.0 MB → ~548 KB gz / ~450 KB br. ~30 lines in one file.
2. **Cache headers on hashed assets** — `public, max-age=31536000, immutable` on
   `/assets/*` (content-hashed filenames, safe) + `no-cache` on `index.html` (so
   upgrades don't strand stale HTML pointing at deleted hashes). Every load after the
   first becomes essentially free.
3. **Lazy-load mermaid core** — convert the static import in `MermaidDiagram.tsx` to a
   dynamic `import('mermaid')` on first diagram render. Drops `App` to ~1 MB min
   (~250–300 KB gz). Trade-offs: first diagram shows a brief loading placeholder;
   `mermaid.initialize()` must run after the dynamic import resolves; the component is
   shared with the Electron renderer, so both builds change behavior (one-time ~100 ms
   parse flash on first diagram — negligible locally).
4. **Optional free latency win** — start `import('@renderer/App')` in parallel with the
   WS handshake instead of after `ready`. Hides the 2 MB fetch behind the
   connect + sync-full round-trip. No chunking change needed.
5. **Then silence the heuristic** — even after #3, `App` stays >500 KB (xterm ~330 KB
   min + react-markdown/unified chain + dompurify + …). Set `chunkSizeWarningLimit` to
   ~1200 in `vite.web.config.ts` so it still trips on real regressions.

If only one thing gets done: **#1 + #2 together** outperform any splitting scheme for
this serving topology (point-to-point from your own machine, repeat usage by the same
devices). The mermaid split (#3) is the only *bundle* change with real payoff.

## Suggested sequencing

- 1 + 2 as one change (server-side, easily tested in `remote-server.test.ts`).
- 3 as a separate change so the renderer behavior change is reviewable in isolation.
