# Bundle size investigation — should we split bundles?

**Date:** 2026-08-13 · **Branch:** `pre-release` · **Trigger:** `(!) Some chunks are larger than 500 kB after minification` from `[5/8] web build`

## Short answer

Splitting is the **third**-best thing we could do, and only for one of the two builds. Two bigger wins sit in front of it, both in `remote-server.ts`.

## What's actually going on

The warning comes only from `[5/8] web build` — the remote client (`src/web`, "ClaudeUI Remote", served over Tailscale). The Electron renderer emits a **4.1 MB** `index` chunk and doesn't warn at all, because electron-vite raises `chunkSizeWarningLimit`.

Two consumers, completely different economics:

| | Electron renderer | Web remote client |
|---|---|---|
| Transport | `file://`, local disk | HTTPS over Tailscale, often to a phone |
| Eager payload | 4.1 MB | 236 kB `index` + 2.14 MB `App` + 95 kB CSS ≈ **2.47 MB** |
| Cost of size | parse/compile only | download + parse on a mobile CPU |

For the renderer, splitting saves **zero bytes** — it only defers parse work on a local disk read. Not worth engineering time.

For the web client it's real. The web entry already lazy-loads `App` (`src/web/main.tsx:233`), so the login screen paints off the 236 kB `index` chunk; the 2.14 MB lands right after auth.

## The two things that beat splitting

### 1. The server never compresses

`src/main/services/remote-server.ts:1472` `serveStatic()` writes `Content-Type` + security headers and pipes the file:

```ts
res.writeHead(200, {
  'Content-Type': mimeTypes[ext] || 'application/octet-stream',
  ...this.securityHeaders(false)
})
fs.createReadStream(filePath).pipe(res)
```

No `Content-Encoding`, ever. Tailscale serve is a plain reverse proxy and won't add it. So a phone pulls **2.47 MB raw** where gzip gives ~640 kB — a **74% cut**, larger than any code-split could deliver, for ~10 lines of `zlib.createGzip()` gated on `accept-encoding`.

### 2. No caching headers

That same path sets no `Cache-Control`, no `ETag`, no `Last-Modified`. Filenames are content-hashed and therefore immutable, but the browser is told nothing — so every reload re-fetches everything. `Cache-Control: public, max-age=31536000, immutable` on `/assets/*` makes the second load free.

Do those two and the 500 kB warning stops describing a real user-facing problem.

## If we still want to split (web only)

Four targeted `React.lazy` / dynamic imports, all currently static:

| Target | Bytes | Where |
|---|---|---|
| `mermaid` core | 421 kB | `src/renderer/src/components/chat/MermaidDiagram.tsx:2` |
| `@xterm/xterm` | 322 kB | `src/renderer/src/components/terminal/XTermInstance.tsx:2` |
| Settings dialog (`settings-sections` + `OpencodeAgents` + `SharedProviders`) | ~125 kB | behind a dialog |
| `cron-parser` | 27 kB | `src/renderer/src/components/automation/AutomationConfig/utils.ts:1` |
| `qrcode` | 24 kB | `src/renderer/src/components/RemoteAccessModal/RemoteAccessModal.tsx:2` |

≈ 900 kB raw off the critical path.

`qrcode` is the standout: `RemoteAccessModal` is a **desktop-only** surface, so those 24 kB are pure dead weight in the web bundle regardless of what we decide about lazy-loading.

**Tradeoff:** on a slow tunnel this runs the other way — opening a terminal becomes a network round-trip instead of instant. Mitigate with a `requestIdleCallback` prefetch after first paint.

**Don't** reach for `manualChunks` vendor-splitting. It's the reflexive answer to this warning and it moves bytes rather than removing them. With immutable caching in place it buys a little cross-update cache retention, nothing more.

## Smell worth a look

`luxon` (71 kB) and `dayjs` coexist in the bundle. `dayjs` is almost certainly mermaid's transitive dep and will fall out for free once mermaid goes lazy — but if any of our own code reaches for both, worth consolidating.

## Recommended order

1. gzip in `serveStatic` (biggest win, smallest diff)
2. `Cache-Control: immutable` on hashed `/assets/*`
3. Re-measure; then lazy-load mermaid + xterm + settings if still warranted
4. Drop `qrcode` from the web path regardless
5. Leave the Electron renderer alone
