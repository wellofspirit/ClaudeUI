# Codex host — implementation spec for ADR-069

One long-lived `codex app-server` host per Codex home and account; sessions are threads on it; reads run on it. The design is [ADR-069](adr/adr-069_codex-host-per-home-and-account.md). This file holds one kickoff per slice and, once a slice lands, a "Landed" paragraph recording the as-built deviations. Worked under ADR-026: the main model writes the kickoff, an implementing agent builds against it, the main model reviews every line, re-runs the gates, has the E2E drives run and reads their evidence, and commits.

## Standing rules for implementing agents

- Never run `git add`, `git commit`, `git stash`, `git checkout`, `git reset`, `git clean`, `git branch`, `git worktree` or `bun install`. The working tree is shared; report the exact list of files you created or changed, and nothing else may differ in `git status`.
- Never run `bun run format` (it rewrites the repo). Format only the files you touched: `bunx prettier --write <file>…`.
- Never delete or rewrite a file you did not create in this task.
- No real credentials, no real sign-ins, no real provider turns. Every process you start runs against an isolated `CODEX_HOME` and the fixture provider (`src/integration/codex/fixture-provider.ts`); never read `~/.codex` or the vault.
- Every behaviour change ships with a guard test proven to FAIL before the change: quote the failing assertion in your report.
- Gates before reporting: `bun run typecheck`, `bun run lint`, the test files you touched, then `bun run test` once. Integration suites run with `CODEX_INTEGRATION=1 bunx vitest run --project integration <file>` (the real binary; gated per host in `src/integration/codex/integration-host.ts`). Quote the summary lines.
- Answer "what does the code do" from the source, not from memory; answer "what does Codex do" from `.cache/codex-src` (tag `rust-v0.154.0`) and by probing the binary, never by assumption.
- Report deviations from the spec explicitly, with the reason.

## H0 — Probes P1–P4 on the real binary

**Goal.** Answer ADR-069's four probe questions with integration tests that stay in the repo as the host contract's guards. No production code changes.

**Facts (verified 2026-09-15).** The fixture provider (`fixture-provider.ts`: `startFixtureProvider`, `writeFixtureCodexHome`, `fixtureAssistantMessage`, the `script` callback receiving every request so far) serves any number of turns; `codex-app-server.integration.test.ts` shows how a test drives `CodexAppServerClient`/`CodexClient` directly against a temp `CODEX_HOME`, scripts a `function_call` to force an approval (`exec_command` with `sandbox_permissions: 'require_escalated'`), and simulates a force-kill (`dispose()`); `codex-lifecycle.integration.test.ts` pins the writer-lock behaviour across processes (`stopHolder` = dispose + 1500 ms). Threads are started with `thread/start`, turns with `turn/start`, and every notification carries `threadId` (`docs/protocol-codex/README.md`, `docs/codex-spike.md` notification catalog). `thread/delete` from a second process is refused with `-32600` while the first holds the writer lock (`delete.ts` header comment). The app-server exits on stdin EOF in stdio mode (`app-server/src/lib.rs`, `stdio_connection_closed`).

**Build** — one new file `src/integration/codex/codex-host-probes.integration.test.ts`, gated like the ADR-068 suites (macOS arm64 and Windows x64), one `it` per probe, each self-contained on a fresh temp home:

- **P1 — three threads, one connection.** One `CodexClient`; `thread/start` × 3; `turn/start` on all three within the same tick; the fixture scripts, for every thread's first request, a `function_call` `exec_command` that needs approval, then on the second request an assistant message. Assert: three `item/commandExecution/requestApproval` server requests arrive, each with the `threadId` of a distinct thread; answering each with `accept` completes exactly that thread's turn (`turn/completed` per thread, three in total); no notification arrives with a `threadId` outside the three; the transport's pending/queued counters never trip a limit (read them through whatever the client exposes, or assert no `queue-limit`/`request-limit` rejection).
- **P2 — resume after a force-killed host.** Host A: `thread/start`, `turn/start` with a scripted response the fixture holds open (never answers), so the turn is mid-flight; `dispose()` A (today's kill). Host B on the same home: `thread/resume` the thread; assert it reopens (`thread` in the response with the same id), `thread/read` shows the first turn either absent or not completed, and a fresh `turn/start` runs to `turn/completed`.
- **P3 — writer lock in a live host.** Host A: `thread/start`, one completed turn, then idle. Host B: `thread/delete` → record whether it is refused (`-32600`) or accepted. Then search the protocol for a way to unload a thread without exiting the process: read `docs/protocol-codex/README.md`'s method list and the generated `src/core/codex/protocol/` method names for anything like `thread/unsubscribe`, `thread/close`, `thread/unload`; if one exists, call it on A and repeat the delete from B; record both outcomes as assertions (`expect(x).toBe(<observed>)` with a comment saying which is the observed fact, so the test documents rather than wishes).
- **P4 — graceful close.** Host with an idle thread: end stdin (`child.stdin.end()`; reach the child through whatever the client exposes, adding a narrow test-only accessor if none exists and saying so) and measure time to `exit` and the exit code; then start a NEW host on the same home immediately and assert it initialises (no `stdout-closed` with exit 1). Repeat with a running turn held open by the fixture: does the server exit on EOF, or wait for the turn? Record the observed behaviour in assertions with comments.

**Report:** the four observed answers in one table (P3 and P4 are facts we do not know yet), the test file, the gate lines, and anything the probes showed that contradicts ADR-069's decisions. Do not change production code to make a probe pass.

**Landed 2026-09-15 (`b2e410ad`, on `pre-release`).** Eight probes (P1, P2, P3, P4 idle, P4 running turn, P5a/b/c) on Windows x64; the answers are recorded in ADR-069 § Probe answers. Deviations accepted: P5 was added mid-slice (the holder's own delete rights, which P3's answer made the load-bearing question); P4 drives its own hand-rolled stdio child because `CodexAppServerClient.dispose()` did not end stdin at the time and ending it behind the transport's back would have measured our kill, while the production transport still does the "next start on the same home" half; the fixture provider gained `FIXTURE_HOLD` (a script may leave a request mid-flight; `close()` destroys survivors) with its own guard, and the probe file was reworked onto the shared provider (1069 → 980 lines, no answer moved). The app-server suite is `darwin && arm64`-gated and could only be collected here; it needs one macOS run after the fixture change.

## H1 — The host primitive: one process per home and account; reads on the host

**Goal.** Introduce `CodexHost` and move every read onto it. Sessions keep their own process in this slice (H2 moves them), so the only behavioural change users see is that reads stop spawning processes.

**Facts (verified 2026-09-15, survey of the code).** Every app-server is built by `CodexClient` → `CodexAppServerClient` (`start()` runs the version probe, the F8 first-run gate, `spawn`, `initialize`, then `auth.inject()` + `account/login/start`). `CodexService` (`src/core/codex/CodexService.ts`) holds a refcounted shared read client (`read()`: first caller starts it with `this.auth`, last caller disposes it) and a per-call client for `startLogin`; its callers each build their own `CodexService` (`CodexAuthProvider` singleton `auth-probe`; `chatgpt-rate-limits.ts` `rate-limits`, disposed per sweep; `codex-config.ts` `config`; `model-discovery.ts` `discovery`, now memoised; `history.ts` `lineage-scan` / `history-list` / `history-read`; `delete.ts` `delete`). `rateLimits(accountIds)` re-injects each account in turn on ONE process (`injectAccount`), which under a per-account host becomes one request per account's host. The identity a process is injected with comes from `codexAuthHook()` (`requestAccount(id)` before `inject()`; `injectedAccountId` after). App quit disposes `codexAuthProvider` and every Codex session (`src/main/index.ts`). `terminate()` is `taskkill /F /T` on Windows and SIGTERM then SIGKILL on POSIX; neither ends stdin first.

**Build:**

1. `src/core/codex/CodexHost.ts` — `class CodexHost` owning one `CodexClient`, created by `CodexHostRegistry.acquire({ home, accountId })` (module singleton, keyed `${codexHomeKey(home)}|${accountId ?? 'native'}`). `acquire` starts the client lazily (version probe, F8 gate, spawn, `initialize`, inject through a `codexAuthHook({ accountId })`) and returns a handle `{ request, release }`; single-flight start; concurrent acquirers share the start. A host tracks its users (handles); when the last handle is released and no session is registered (H2), an idle timer (`CODEX_HOST_IDLE_MS`, default 5 minutes) closes it. Any transport failure closes the host, rejects every open handle's in-flight request through the existing error, logs the F7 line with label `host`, and removes the host from the registry so the next `acquire` starts a fresh one; it never retries on its own.
2. **Graceful close** in `CodexAppServerClient`: `dispose()` ends stdin first, waits up to `killGraceMs` for `exit`, then runs today's `terminate()`. The F7 death line is NOT logged for a close the client initiated. Guard: a fake child whose stdin `end` is observed before any kill, and a child that ignores EOF is killed after the grace.
3. **`CodexService` becomes a facade over hosts.** `read()` acquires the host for `this.accountId` (the service is constructed with an account: `null` = active vault account, resolved at acquire time) instead of starting a client; `rateLimits(accountIds)` acquires one host per account and asks each `account/rateLimits/read`; `startLogin` keeps its own dedicated client (it must run WITHOUT injection, by design). Every caller passes its label into `acquire` for the spawn line; the label of the process becomes `host`, and the per-caller label is logged per acquire at debug (`host acquired: <label> …`).
4. **The 30-second poll** (`session.ipc.ts` `DIRECTORY_POLL_MS`) needs no change once `listCodexSessions` runs on a warm host, but it must not keep the host alive forever: the idle timer counts from the last release, and a poll every 30 s on a 5-minute timer would. Rule: reads do not reset the idle timer; only registered sessions (H2) keep a host alive. Note it in the docs.
5. App quit: `src/main/index.ts` disposes the registry (all hosts, graceful, bounded) instead of the auth provider's own service.
6. Guard tests (unit, mocked transport, proven failing first): two acquires share one start; release-to-zero starts the idle timer and the timer closes the host; a read during the idle wait cancels it; a transport failure removes the host and the next acquire starts a new one; two accounts get two hosts; graceful dispose ends stdin before killing; `rateLimits` for two accounts uses two hosts and never `injectAccount`s across them. Rewrite the `codex-service.test.ts` assertions that pin one-client-per-read to the host contract.
7. Docs: `docs/architecture/codex.md` transport and ownership sections (host, registry, idle rule, graceful close); the F8 paragraph notes the gate now guards host starts.

**Report:** files, gates, failing assertions quoted, the idle rule as implemented, and the live check the reviewer will run: `CLAUDE_UI_LOG=CodexAppServerClient node scripts/codex-render-stress.mjs --iterations 3` must show one `host` spawn for the reads and no `discovery` / `history-list` / `lineage-scan` / `auth-probe` / `rate-limits` spawns.

**Landed 2026-09-15 (on `pre-release`).** As specified, with these deviations accepted: `CodexServiceOptions.identity` replaces `auth` (the host builds the one hook per process); a gracefully closed child is still tree-killed the moment it exits, not only after the grace (keeps the descendant guarantee and narrows the pid-reuse window); the host answers `account/chatgptAuthTokens/refresh` from its hook (ADR-069 §8); `codexAuthProvider.dispose()` left the quit path (it only cancelled a login that provider never starts). Two reviewer rulings applied: the identity buckets were merged so `{ accountId: null }` with no active vault account resolves to `native` (inject nothing) and every product reader — config, history, lineage, delete included — asks for the active account, so a machine runs ONE host per home in the common case (a source-scan guard pins that no reader constructs a `CodexService` without an identity); and the four integration suites that reach the registry dispose it in `afterEach`, because a service no longer ends a process. The idle rule is a deadline, not a sliding window: fixed the first time a host falls to zero users, cancelled by a read in flight and re-armed for the remainder, cleared only by `retain()` (the H2 seam). Verified: typecheck, lint, the codex unit directory (26 files, 514 tests), full `bun run test` (675 files, 12557 tests), the four Windows-enabled integration suites with `CODEX_INTEGRATION=1` (config-write 5, injection 5, mcp-approval 2, mcp-override 3), and live on a fresh home with `CLAUDE_UI_LOG=CodexAppServerClient,CodexHost`: one `host` spawn served the lineage scan, the listing and both boot discoveries, no `app-server closed` line, three sessions each spawned their own process as this slice intends, 3/3 turns clean. Not verified here: the four macOS-only suites that gained the registry teardown (`codex-app-server`, `codex-delete`, `codex-interrupted-tool`, `codex-lifecycle`) need one macOS run. Known window until H2: a delete issued while the warm host has the thread's fork loaded behaves per P5c (leaf-first still required), unchanged in shape.

## H2 — Sessions as threads on the host

**Goal.** `CodexSession` stops owning a process. It attaches to the host for its account, starts or resumes its thread there, and every notification, server request and abort is routed to it by `threadId`. Deletes run on the host that holds the thread. The dispatch target becomes a thread on the caller's host. After this slice the only app-servers ClaudeUI runs are hosts (one per home and account) plus `startLogin`'s dedicated uninjected client.

**Facts (verified 2026-09-15).** From H1 (`src/core/codex/CodexHost.ts`): `codexHostRegistry.acquire({ identity: { accountId }, cwd, env, label })` returns a `CodexHostHandle { request, injectedAccountId, host, release }`; `host.retain()` / `host.release()` are the empty seams for sessions (a retained host never idles out); a host closes on transport death or `close()`, rejects every handle afterwards, and the registry forgets it. `CodexAppServerClient` routes server requests through `serverMethods` and an `Incoming` record that scrapes `threadId`/`turnId` off the params (`abortServerRequests(threadId, turnId)` matches both); notifications reach one `onNotification(method, params)`. From the survey of `CodexSession.ts` (line numbers as of 239b7136): the client is a `readonly` field built in the constructor from `createClient` with `serverMethods` (`:100-117`), `onNotification` (`:572`), a four-way `onServerRequest` by method with no thread dimension (`:573-580`), `onDisconnect` (`:581`); `threadId` is assigned from `thread/start`/`resume`/`fork` (`:952`); every foreign `threadId` is treated as a child of this root (`:1411-1416`, `childNotification`/`childHold`/`registerChild` `:1644-1677`); `account/rateLimits/updated` carries no `threadId` and is attributed to `injectedAccountId` (`:1397-1410`); approvals and elicitations accept only own thread or a registered child (`:2576-2592`, `:2494-2520`); `approvalRequestId` is `codex-approval:${generation}:…` with `generation = randomUUID()` per session (`:447`, `:2400-2407`); `hostedCalls` dedupe per generation (`:500`, `:2248`); `dispose()` = `disconnected()` then `client.dispose()` (`:1294-1298`); `interrupt()` failure disposes the whole client (`:1285-1288`); `applyPin` re-points the live process with `client.injectAccount` (`:1165-1183`); `start()` injects before the thread exists (`:821-831`). Dispatch target (`cross-engine-dispatcher.ts`): `createCodexTarget` spawns a `CodexClient` per target with `CODEX_TARGET_SERVER_METHODS` (four approval methods), starts it with the caller's pin or the active account (`:4365-4374`), reads config and the catalog, then `thread/start` without `dynamicTools`; `disposeFor` kills the child; the same-engine guard refuses codex → codex (`dispatchInner`). Delete (`delete.ts`): a live node is stopped through `CodexDeleteHooks.stop` (wired to `manager.cancel`) and the walk retries a just-stopped node for `STOPPED_HOLDER_RETRY_MS` because the writer lock outlives the stop. App quit disposes every Codex session (`main/index.ts`). Probe answers (ADR-069 § Probe answers): P1 thread isolation holds on one connection; P2 a resumed thread carries the dead turn as `status: "interrupted"`; P3/P5 the writer lock is process-scoped, the holder can `thread/delete` its own loaded thread (idle: gone; running: interrupts, `turn/completed` envelope with `turn.status: interrupted`), a source with a loaded fork is refused from the holder too; P4 stdin EOF exits in milliseconds. `thread/unsubscribe` exists on the binary but is absent from the generated `protocol/methods.ts` (add it to `scripts/generate-codex-protocol.mjs`'s selection and regenerate; `bun run check-codex-protocol` must pass).

**Build:**

1. **Thread connections on the host.** `CodexHost.attach(owner: CodexThreadOwner): CodexThreadConnection`, where the owner supplies `onNotification(method, params)`, `onServerRequest(method, params, context)`, `onDisconnect(error)`, and the connection offers `request()`, `abortServerRequests(threadId, turnId)`, `claim(threadId)` / `disclaim(threadId)` (the root's own id and every child it binds), and `detach()`. The host keeps one demultiplexer: a notification or server request whose params carry a `threadId` goes to the owner that claimed it; one without a `threadId` (`account/rateLimits/updated`, `account/…`) is fanned out to every attached owner; `account/chatgptAuthTokens/refresh` stays the host's own; a server request for a thread nobody claimed is answered with the transport's method-not-found error and logged once at debug (never silently accepted — a lost approval must be visible); a notification for an unclaimed thread is dropped, as a foreign child's is today. The host's `serverMethods` become the union the sessions need (today's `SERVER_METHODS` list in `CodexSession.ts`) plus the refresh. `attach` retains the host; `detach` releases it and, when the owner has claimed threads, sends `thread/unsubscribe` for each so a dropped session stops the firehose for a thread that stays loaded.
2. **`CodexSession` on the host.** Replace `createClient` and the `readonly client` with an attach in `start()`: acquire the host for `pinnedAccountId() ?? active` (the identity the session runs as; `injectedAccountId` comes from the host), attach, `claim` the thread id once `thread/start`/`resume`/`fork` answers, keep `registerChild` claiming child ids. `generation` becomes the host's generation (a counter bumped per host start, exposed on the handle), so an approval or hosted call minted for a previous host is refused after a resume exactly as a previous process's is today. `dispose()` = interrupt the running turn if any, close child cards, detach; no process kill. `disconnected(error)` stays the single funnel and is what the host calls on death for every attached owner. `interrupt()` failure detaches this session only. `applyPin` on a live session: interrupt, detach, acquire the target account's host, `thread/resume` there, re-claim; when the session is idle this is one resume, and the pending-pin path at the turn boundary stays.
3. **Delete on the holder.** `deleteCodexThread` and the subtree walk issue `thread/delete` on the host that has the thread claimed when one does (the registry answers `hostFor(threadId)` from the claims), else on the active host. The `stop` hook keeps disposing the live session first (it interrupts and detaches; the thread stays loaded, which P5 shows is fine for the holder). Remove `STOPPED_HOLDER_RETRY_MS` and its retry loop: a same-host delete is immediate. The leaf-first walk and the fork refusal stay.
4. **Dispatch target as a thread.** `createCodexTarget` attaches to the caller's host (the caller's pin, else active) instead of spawning; `disposeFor` interrupts and detaches; the `CODEX_TARGET_SERVER_METHODS` become the target owner's routing. Lift the same-engine guard for `codex → codex` only (ADR-033 amendment recorded in the ADR's As built), keeping the refusal text for the other engines.
5. **Quit** disposes the registry only; the per-session Codex sweep in `main/index.ts` goes (sessions no longer own processes), and `SessionManager.cancelAll` still interrupts turns.
6. **Guard tests, each proven failing first:** host demux unit tests (two owners, notifications routed by `threadId`, an unclaimed thread's server request answered method-not-found and logged, a `threadId`-less notification fanned out, detach unsubscribes, host death calls every owner's `onDisconnect` once); `codex-session.test.ts` rewritten where it asserted `client.dispose` (fork mismatch, native child adopted as root, interrupt before a thread, unsupported provider, "disposes pending approvals and transport exactly once", "never accepts a prior process generation approval after resume" → prior HOST generation) and the premise comment at `:2299`; `codex-delete.test.ts`: no stop-then-wait, delete issued on the holder; dispatcher tests for the Codex target as a thread; a new integration suite `codex-host-sessions.integration.test.ts` (gated like the ADR-068 four): two `CodexSession`s on one host with concurrent turns and one scripted approval each (P1 through the session layer), a session disposed mid-turn leaves the other untouched, host death marks both `disconnected`, and a resume after host death renders the interrupted turn. Keep `codex-app-server.integration.test.ts` green: the root-plus-native-children probes now run on a host.
7. **Docs:** `docs/architecture/codex.md` ownership table (the session row loses "process"; the host row gains the demultiplexer and claims), the identity paragraph (host generation), `docs/protocol-codex/README.md` "M1b service and ownership" (a later root adapter no longer owns a separate client), ADR-069 § As built.

**Report:** files, gates (unit directory, full suite, the Windows-enabled integration suites with `CODEX_INTEGRATION=1`), the failing assertions quoted, the demultiplexer's routing rules as built, and what a `disconnected` session shows after a host death (the renderer contract of ADR-045 must be unchanged).
