# Multi-engine architecture & auth

Part of [architecture/](README.md).

## Multi-engine architecture

The V2 model (ADR-018) separates **Engine** (harness: `claude` | `opencode` | `pi` | `codex`) × **Vendor** (model maker) × **Account** (billing/auth identity). `ModelRef {engineId, vendorId, modelId}` is the universal selection/persistence key; `engineId` is immutable per session, model/account/capabilities re-resolve on model switch.

Codex is the **fourth engine**: registered in `register-engines.ts`, in `EngineId`, and selectable once native catalog discovery finds the installed pinned binary. It runs under the shared permission modes and rules like every other engine ([ADR-067](../adr/adr-067_codex-shared-permission-model.md)); Auto hands review to Codex's own `auto_review` guardian rather than ClaudeUI's judge. [ADR-066](../adr/adr-066_codex-fourth-engine.md), the [architecture](codex.md), and the [handoff](../codex-integration-handoff.md) cover the rest, including what is still open (metering attribution, Windows and Linux turn verification); queue and steer, hosted tools, dispatch in both directions, completed-turn fork, native children and tree-walking delete are built. Authentication is moving to the vault-owned ChatGPT identity of [ADR-068](../adr/adr-068_chatgpt-identity-vault-owned-codex-injection.md): Codex is a third route of the shared `chatgpt` provider, fed by token injection rather than a file, with N accounts and opt-in per-session pinning. Until that lands the built path is Codex-native device-code login.

- **Session seam** — `src/core/providers/`: all backends implement `ISession`; `SessionManager` holds `Map<routingId, ISession>`; the renderer consumes the same `session:*` events regardless of engine. `SpawnPrepRegistry` applies per-engine spawn env (unknown engine throws). `shared/engine-meta.ts` is the per-engine descriptor table — adding an `EngineId` is a compile error until its meta exists.
- **Capabilities** — `EngineCapabilities` × `ModelCapabilities` → `ResolvedCapabilities` (`shared/model-capabilities.ts`), recomputed on session start and model switch; the renderer gates every feature on it. Per ADR-030, a flag is only `true` when the full end-to-end path works.
- **opencode backend** (opencode 2.x only since [ADR-093](../adr/adr-093_opencode-v2-only.md); ADR-019's design amended) — ONE `opencode serve --stdio` per distinct config injection, not per cwd: the directory travels per request (`x-opencode-directory`), the server's lifetime is its stdin (as pi, ADR-092), leases are ref-counted per directory and released exactly (`OpencodeServerManager`). The typed `OpencodeClient` (generated from the pinned OpenAPI spec) and one server-wide SSE feed with no replay (a reconnect re-reads state). `OpencodeSession` maps the feed through its S4 mapper (`v2-event-mapper.ts`, cold history `v2-history.ts`) to the neutral `session:*` contract; prompts and the queue ride opencode's native inbox (§9, superseding ADR-053's host-held queue for opencode). Permissions compile to 2.x `{action, resource, effect}` session rulesets (ADR-022 as amended, `permission-v2.ts`); every reject carries a message (a messageless one ends the turn); subagent children get their own ruleset (`child-rulesets.ts`); the `claudeui-xeng` directory plugin keeps the user's saved "always" rows from answering ClaudeUI's asks and is REQUIRED for a turn (fail closed). Auto mode uses ClaudeUI's judge (ADR-023/088); credentials are vended into opencode's DB (§5); config edits write 2.x keys (§6/S8, ADR-028/029/031 as amended). Wire reference: `docs/protocol-opencode/`. The 1.x adapter (`OpencodeV1Client`, `OpencodeV1Session`, `event-mapper.ts`, `protocol/`) is dead code removed at S10.
- **pi backend** (ADR-035) — a `pi --mode rpc` child process per session (LF-framed JSONL over stdio, no server — the claude-shaped lifecycle); `PiSession` maps events to the neutral contract in `src/core/pi/event-mapper.ts`. pi has no native permissions and no MCP client, so a ClaudeUI-owned `-e` bridge extension (`pi-bridge-source.ts`) POSTs `tool_call` decisions to a per-session loopback `PiBridgeHost` (evaluated by the pure `permission-engine.ts` against the SAME `~/.claude` rules Claude/opencode use — ADR-022 parity), and registers the hosted tools + `dispatch_agent` via `pi.registerTool()` over the same host. Auth reads/writes pi's own `auth.json` (ADR-021); shared skills via the extension's `resources_discover`. Details + verified wire facts: `docs/protocol-pi/`.
- **Model catalogs follow the harness** (ADR-082) — pi and opencode discovery cache what the binary they probed reported (`src/core/pi/model-discovery.ts`, `src/core/opencode/model-discovery.ts`); a harness install, uninstall, update or selection change replaces that binary, so its catalog goes too.
  - _One change token._ `harnessRevision(id)` (`src/core/harness/resolve.ts`) hashes source, path, stated version, whether it runs, and the file's size and mtime. A detection run that changed nothing keeps it — and keeps a warm catalog.
  - _Main._ `harness/catalog-invalidation.ts` drops an engine's model, catalog, capability and empty-result caches when its revision moves.
  - _Renderer._ `harness:state` carries it as `resolved.revision`; the harness store reports a change (`followRunChanges`) and the session store reloads THAT engine (`reloadEngineModels`: its composer counter plus the global `modelReloadNonce` every open model sheet follows), composer mounted or not. The provider registry is re-read once pi's catalog is warm.
  - _Per engine_ (ADR-092). The composer asks `getEngineModels(engineId)` once per engine and each answer fills only its own slice of `availableModels`, in fixed engine order, so a slow probe holds back only its own models. A failed pi probe backs off 5 s and re-probes once; when a catalog fills after a degraded `[]` was served, main emits `engine:models-changed` and clients reload that engine. The boot credential sync is idempotent, so an unchanged key never invalidates a catalog.
  - _Generations._ An invalidation kills the probe in flight; it cannot write a cache. A public read returns only what its own generation answered, checked after its last await; an overtaken caller asks again at most twice, else gets `[]`.
  - _opencode servers._ Discovery reads `/api/integration` + `/api/provider` + `/api/model` on ClaudeUI's own (global) pooled server, never a project's (ADR-093 §5 as built, S7); a cold, empty model list is re-read until authoritative and never negative-cached. `opencode serve` starts take turns: two processes migrating opencode's one database at once race and the loser exits. A start queued at shutdown never spawns.
  - _Live sessions_ keep their model and process; a new binary applies to what spawns next.
- **Cross-engine dispatch** (ADR-033) — a hosted `dispatch_agent` tool lets a session on any engine delegate to a headless target on another, with subtask-style TaskCard streaming, forwarded approvals, cost cap, and usage attributed to the dispatching session. pi participates both directions (ADR-035): as a source via a `registerTool` dispatch tool, as a target via a headless `PiRpcClient` + per-target `PiBridgeHost` (recursion structurally impossible — a target's child never gets the dispatch tool). An opencode target (2.x, ADR-093 S9) is a session on its own exact lease with the shared per-SERVER feed, driven by an inbox prompt and settled by its own S4 mapper; asks walk the session's host pre-check, then ClaudeUI's judge or a card. As a source, opencode names the caller in `_meta["ai.opencode/sessionID"]`; a subagent child's call is resolved through `parentID` to the chat it descends from.
- **Tool rendering** — engine tool names map to a neutral `ToolKind` taxonomy (`shared/tool-kinds.ts`); kind bodies under `renderer/.../tool-registry/kinds/` consume an engine-neutral `ToolView`. The per-engine `kindOf` switches in `ClaudeEngineToolMap.ts` / `OpencodeEngineToolMap.ts` / `PiEngineToolMap.ts` / `CodexEngineToolMap.ts` are the canonical mapping tables.

## Auth / accounts

`EngineAuthProvider` (`src/core/auth/`, ADR-021) is the per-engine auth abstraction with capability-gated method groups: `probe()` (always), sign-in driving (`canDriveLogin`), and account CRUD (`multiAccount`). The interface lives in core, but not every implementation does: `ClaudeAuthProvider` (and `EngineAuthRegistry`) stay in `src/main/auth/`, because Claude sign-in opens the host browser (ADR-058 — `HostAuth` exposes only their reads to core).

- **`ClaudeAuthProvider`** wraps `AuthManager` + `AccountManager`: native OAuth rides cli.js control requests on the service session (ADR-014); multi-account uses app-owned per-account credential files whose access token each spawn is handed through `CLAUDE_CODE_OAUTH_TOKEN`, kept fresh by the token keeper (ADR-015; `core/services/claude-host-token.ts`). `probe()` derives auth state from the cached `session:auth-source` signal — no reads of cli.js's credential store (avoids Keychain prompts); in multi-account mode that signal comes from the active account's own file, because cli.js reports no email for a host token. Account metadata lives in the DB (`account` table); the `enabled`/`activeId` pointer stays in `accounts.json`; credentials stay file-based, never in the DB.
- **`OpencodeAuthProvider`** (opencode 2.x, ADR-093 §5) reads `/api/integration` + `/api/provider` + the credential snapshot (types and ownership of each integration's ACTIVE row, never a value); keys are ClaudeUI's own `cred_claudeui_*` rows in opencode's DB, OAuth sign-ins run on opencode's integration flows. ClaudeUI no longer reads or writes opencode's `auth.json`.
- **`CodexAuthProvider`** probes through a read-only `CodexService` (native account status plus visible model count) and drives Codex's own device-code login; Codex owns credential storage and refresh, and no host browser is opened.
- **One sign-in dialog** (ADR-068 §3, Slice 3): `SignInDialog` is the only surface that renders a sign-in flow, for Anthropic (cli.js drivers, ADR-014) and ChatGPT (the vault's PKCE, ADR-036/057). Every entry point opens it through the store's `signInDialog` slice. In the chat there are exactly TWO since ADR-070 §4 — the app-wide `AuthPill` in the top bar's left group and the engine-neutral `AuthTranscriptRow` over the session's `authRequired` (all four engines raise `session:auth-required` — pi since `0a8d80a9`, whose classifier treats a 401/403 turn error, and only those, as a rejected credential) — both reading the one `authIssues` view so they cannot drift; `AuthBanner`, `AuthRequiredRow` and the composer's `signInHint` are deleted. Outside the chat: the settings account rows and provider sheets, and the model picker's and mobile sheet's dimmed groups. `VendorOAuthFlow` survives for opencode-native vendor OAuth only.
- **The ChatGPT vault holds N accounts** (ADR-068 §2, Slice 1): `~/.claude/ui/auth-vault.json` v3 keeps API keys under `credentials` and OAuth subscriptions under `accounts.<provider>.{activeId, list}`; `CredentialSync` refreshes every account on its own timer and vends only the ACTIVE one to pi and opencode; the `provider-account:*` commands (list/switch/remove/set-per-session, `config`, both transports) and the ChatGPT Manage sheet's Accounts card sit on top. Adding an account is the existing vault PKCE sign-in, whose completion upserts by workspace id.
- `session.account: AccountRef | null` rides every `SessionStatus`; `AuthState` is the tri-state `'authenticated' | 'unauthenticated' | 'unknown'`, while the login-flow object is `AuthFlowState`.

### In-app Claude sign-in (multi-account)

`AuthManager` keeps one state machine (flow ids, settle/replay, remote vs desktop, the half-copied paste, cancel, `finalize`'s side effects) and puts the sign-in itself behind `ClaudeLoginBackend` (`src/main/services/claude-login-backend.ts`), picked when a flow starts:

- **Single-account** — cli.js's `claude_authenticate` / `claude_oauth_wait_for_completion` / `claude_oauth_callback` on the service session ([protocol-cc §7.5](../protocol-cc/07-control-outbound.md)), unchanged; cli.js stores the login in the user's own Claude Code store.
- **Multi-account** (an active account dir) — `ClaudeLoginFlow` (`src/core/auth/claude-oauth.ts`, Electron-free) runs cli.js's claude.ai login itself: the same authorize URL, params and scopes (`_Ln` / `kCr()`), PKCE S256 + a random `state`, a single-use loopback listener on `127.0.0.1:<random>/callback` that verifies `state` and 302s to cli.js's success page, or the pasted `code#state` exchanged against `MANUAL_REDIRECT_URL`. After the JSON code exchange it reads `/api/oauth/profile` (tier, email) and `/api/oauth/claude_cli/roles` (organization name), as cli.js's login does. A remote sign-in (ADR-057) binds no listener at all. A flow that waits 10 minutes for a code times out; one whose account stops being the active one is cancelled, as a cli.js flow dies with the service session on a switch.

It writes **`<accountDir>/.credentials.json`** atomically, 0600, keeping every other top-level key, with `claudeAiOauth` in cli.js's own shape (`ILn` → `ab()`): `accessToken`, `refreshToken`, `expiresAt`, `refreshTokenExpiresAt`, `scopes`, `subscriptionType` (`max`/`pro`/`team`/`enterprise` from the profile's `organization_type`, else the file's prior value, else `null`), `rateLimitTier`. The account dir is captured when the flow starts. It writes nothing to `~/.claude.json`. The `oauthAccount` block there is shared by every dir, and cli.js rewrites it only when it refetches the profile (a missing field, or older than 24 h), so after an in-app login it can name another account until then — the same staleness `claude-account-identity.ts` already works around for usage.

Remote-access authentication (tokens, passwords, tailnet identity, and the target passkey model) is a separate concern: [security.md](security.md) and ADR-039/052.
