# Remote security model — SyncCore

Part of [architecture/](README.md). **Status:** **implemented** (ADR-052 + ADR-054 + ADR-056) — passkeys landed 2026-08-15, the step-up TIERS and the host anchor alongside them, and the ADMISSION MODEL rework (ADR-056) on 2026-08-17; companion to [sync-core.md](sync-core.md). ADR-039/042 remain in force for transport hardening throughout. Sections below describe what is BUILT unless a line says otherwise; the code of record is `src/core/services/webauthn-service.ts` (ceremony), `auth-policy.ts` (login modes and grants), `step-up-tier.ts` (the post-login freshness table — the single classification source), `remote-server.ts` (origin classification, handshake, tier enforcement, session cut), `src/core/ipc/webauthn-commands.ts` + `authcfg-commands.ts` (management verbs), `src/web/connection.ts` + `src/web/step-up-gate.ts` (client state machine and the generic ceremony gate).

**THE RULE (ADR-056).** *The link is the channel, never the identity — identity is a passkey or a password.* A URL fragment can carry a **channel key** (`#k=`), which opens an encrypted pipe and buys nothing else; what a connection may then DO is decided by the credential it presents inside that pipe. The one exception is the enrollment link, which is a single-use `enroll`-only credential and is bounded accordingly.

**The two axes.** ADR-052 conflated *how a connection gets in* with *how fresh its presence proof must stay afterwards*; ADR-054 split them, and every section below belongs to one or the other:

| Axis | Setting | Owned by | Sections |
| ---- | ------- | -------- | -------- |
| Login ceremony | `remoteAuthPolicy` (`AUTO` / `passkey-always` / `off`; `password` is AUTO's zero-credential answer, resolved never stored) | `auth-policy.ts` | Identity & authentication methods, Policy modes, Capability grants |
| Post-login freshness | `stepUpTier` (`strong` / `medium` / `off`) | `step-up-tier.ts` | Step-up tiers, Grant decay, Terminal posture |

## Posture & threat model

- **Single operator.** All clients are the owner's devices; there is no per-person permissioning (non-goal).
- **Honesty about authority:** any authenticated remote client is *already* operator-level in effect — model-mediated execution (auto mode, remote approvals, full `git:*` including push) is equivalent to code execution on the host. A raw terminal adds immediacy, interactivity, and the absence of an approval gate — not new authority. The design goal is therefore not containment theater but making powerful access **deliberate** (explicit grants + step-up), **attributable** (per-connection identity), and **observable** (audit log, multi-attach visibility).
- **Transport:** `tailscale serve` TLS, tunnel + E2E, LAN + E2E, Host allowlist, XFF-keyed throttling, funnel reject (ADR-039), pinned HTTPS port (ADR-042).

### What LAN E2E does and does not cover (accepted risk)

ADR-056 gave the plain-LAN origin its own E2E channel, and the boundary of that is worth stating precisely, because the tempting summary — "plain LAN is no longer plaintext" — is **false**.

**Covered:** the WebSocket lane. Every frame from `e2e-activate` onwards is AES-256-GCM, so the password proof, the session snapshot, chat content, terminal traffic and the scoped route tokens are no longer readable by a passive observer on the wire.

**How that cipher runs here is not the same as elsewhere.** A browser exposes `crypto.subtle` only in a secure context, and this origin is plain HTTP — so on the LAN link (and only there) the channel's HKDF-SHA256 + AES-256-GCM run in **pure JavaScript** (`@noble/hashes` + `@noble/ciphers`) rather than through Web Crypto, which every other origin still uses. Same algorithm, same key derivation, same wire bytes — the two interoperate, and they must, because the server end of a LAN session is always on Web Crypto. The one difference that matters to this section: the pure-JS path necessarily holds the derived key as raw bytes instead of a non-extractable `CryptoKey`. See ADR-056's 2026-08-18 amendment; without the fallback the LAN channel was unopenable from any browser at all.

**NOT covered — still plain HTTP on the LAN origin:** the `/remote` bundle itself, `/assets/*`, `/remote/auth-info` (which carries the salt and KDF params), `/mockup/*` and `/sent-file`. So:

- A **passive** LAN observer learns that a ClaudeUI exists, its salt/KDF params, and the contents of any delivered file or mockup fetched over that origin — but not the WS lane.
- An **ACTIVE on-path attacker still wins outright.** They can rewrite the served bundle, and the rewritten bundle reads the `#k=` fragment out of the URL and the password out of the form. E2E on the WS lane does not help, because the code performing it is code the attacker supplied.

This is an **accepted risk, not a fix**: closing it means TLS on the LAN listener (a certificate story ClaudeUI does not have) or refusing the origin entirely. **LAN remains the weakest origin, and `tailscale serve` is the recommended one** — it is the only origin where the whole surface, bundle included, is authenticated and encrypted end to end. The LAN link exists because it is the fallback an operator reaches for precisely when the tailnet is not up, and its channel key is a real improvement over a bearer token in the same fragment; it is not a substitute for TLS.

### Origin classification — one function, three consumers

`classifyConnectionOrigin` (`remote-server.ts`) is the single answer to "where did this connection come from", and it decides three things that must never disagree: which E2E key an `e2e-activate` is measured against, whether a plaintext socket is acceptable at all, and whether there is a username hint to attach. A second classifier would be a plaintext side door, so there is one — consulted by E2E selection, by the auth requirements, and (as a belt behind `verifyClient`) by the funnel reject.

**`Host` IS NOT AN INPUT, and the exclusion is directional.** Every value the classifier reads is the socket PEER, a header the ADR-039 trust predicate has already vouched for, or this server's own run state. `Host` is attacker-controlled, so it may only ever be used to UPGRADE what a connection must present — it still selects the WebAuthn origin, where being wrong costs a ceremony that cannot succeed — and never to downgrade it. The first implementation of this function read the tunnel arm off `Host`, and a tunnelled client sending `Host: localhost:<port>` therefore classified `localhost`, dropped its E2E requirement, and completed a plaintext handshake through the one transport that must never allow one.

The ORDER of the remaining tests still matters, because the obvious implementation is wrong the other way too: **both trusted proxies run on this machine and connect to our own port**, so their sockets have LOOPBACK peers. The order is: `funnel` (refuse, compute nothing else) → **any non-loopback peer ⇒ `lan`** → then, among the loopback peers: trusted serve identity headers (`isServeProxied` plus the `Tailscale-Headers-Info` marker — the SAME predicate the identity layer trusts, not a private copy) ⇒ `tailnet-serve`; else this run holding a tunnel key ⇒ `tunnel`; else ⇒ `localhost`.

That tunnel arm is unconditional on run state rather than on the address asked for, and it has a cost worth naming: while a tunnel is up, a genuine localhost browser is classified `tunnel` and must use the tunnel link. That is the same behaviour as before ADR-056 (the old server demanded E2E whenever a tunnel key existed), and it is the safe direction of an ambiguity we cannot otherwise resolve — a cloudflared forward and a local process are the same socket from here.

## Identity & authentication methods

### 1. Passkeys / WebAuthn — primary

- **Mechanics:** enrollment creates a keypair in the device's authenticator (Secure Enclave / StrongBox / Windows Hello); the private key never leaves it and is gated by the device biometric (`userVerification: required` — FaceID/fingerprint *is* the UV we verify). Authentication is challenge–response: server issues a random single-use challenge (~2 min TTL, server-side state), the authenticator signs after the biometric gate, the server verifies against the stored public key. Unlike the static scrypt proof, an assertion cannot be silently replayed — which is what makes grant decay (below) actually prove human presence.
- **Storage:** `webauthn_credential` table in the operational DB (migration v11): `{credId PK, publicKeyCose, transports, nickname, createdAt, lastUsedAt, backedUp, aaguid, signCount}`. Single-operator ⇒ one fixed user handle, and **discoverable credentials** ⇒ no username step: open the page, biometric, in. A stolen DB leaks public keys only.
- **Sign counters are recorded, never enforced** — and that is a deliberate ACT, not an omission. `@simplewebauthn/server`'s `verifyAuthenticationResponse` enforces counter regression by default; `webauthn-service.ts` feeds it `counter: 0` for every credential, which is the documented way to opt out. Synced passkeys (iCloud Keychain, Google Password Manager) legitimately report 0 forever, so the default would lock out exactly the credentials this design is built around. The stored `sign_count` is updated on each assertion for forensics only.
- **Multi-device:** one row per credential. Synced passkeys make one enrollment cover an ecosystem — the `backedUp` flag is surfaced in the desktop credential list ("Synced" badge vs "Only on that device"), because revoking a synced credential removes it everywhere it syncs to. Cross-ecosystem use rides WebAuthn hybrid transport (QR + BLE) for free.
- **RP ID constraint:** passkeys bind to the serving domain, so the RP ID comes from the request `Host` the allowlist already validated — never from anything the client asserts about its own context. Exactly two origins qualify (`resolveWebauthnOrigin`): the tailnet DNS name (`<machine>.<tailnet>.ts.net`) and `localhost` for development. Machine/tailnet rename invalidates credentials → re-enroll (accepted).

### Origin × channel × identity matrix (ADR-056, as built)

Two columns, because ADR-056 separated the two questions the old matrix ran together. **Channel** is what makes the socket confidential; **identity** is what makes it authorized. A link can only ever be the first.

| Origin | Channel | Identity |
| ------ | ------- | -------- |
| Tailnet HTTPS (`tailscale serve`; secure context, stable RP ID) | TLS, terminated by serve. **No fragment secret in the URL at all** | Passkey ceremony per policy mode; break-glass password when enabled |
| Cloudflared tunnel (ephemeral hostname) | E2E, **ephemeral** key that dies with the tunnel (`#k=`) | **Password, REQUIRED**, presented inside the ciphertext. A passkey is impossible (no stable RP ID) |
| LAN direct (IP; not a secure context) | E2E, **persistent** key stored in `remote_config.lan_e2e_key` and rotatable (`#k=`) | **Password, REQUIRED**, inside the ciphertext. Likewise no WebAuthn |
| localhost dev | none needed (already local + a secure context) | As on the tailnet: ceremony per policy, password where provisioned |
| The host's own surface — desktop renderer (MessagePort) or server console | The port / the console IS the trust | none — never any ceremony. `method: 'host'`; the `label` says which surface (`desktop-renderer` / `server-console`) |

Three consequences worth stating plainly:

- **The handshake ORDER inverts on the E2E origins.** `e2e-activate` comes FIRST and proves possession of the channel key; the `auth` frame — password proof or enrollment token — travels inside the ciphertext, and so does every server answer including the refusals. On tailnet/localhost the handshake is unchanged (auth frame first, no E2E).
- **A plaintext socket on a LAN origin is REFUSED** (close 4004), and that is the same rule rather than an extra one: on an E2E origin nothing is read in the clear, so a plaintext first frame is a socket that never proved the channel. localhost and serve-forwarded sockets are exempt because their transports are already confidential.
- **A channel with no identity is refused with a typed `password-required`**, which the client renders as *"provision a password on the host to use this link"*. It spends no failure budget: nothing the caller did was wrong, and nothing they can do from the phone will help. Starting a tunnel with no password provisioned is still allowed — the status surface carries the same warning.

The `passkey-always` ceremony requirement applies to connections arriving on a **WebAuthn-capable origin**. On the others `passwordAuthAllowed` / `passwordStepUpAllowed` deliberately ignore the `passkey-only` toggle — honouring it there would leave LAN and tunnel with **no admission credential at all**, which is not what "passkey only" means to whoever set it, and is how people lock themselves out.

### 2. Password — break-glass, and on two origins the ONLY way in (scrypt, per ADR-039)

**Enabled by default** (owner decision); a "passkey-only" toggle disables it *where a passkey is possible*. Recorded caveat: the proof is deterministic and client-cacheable, so it authenticates the *client*, not provably the *human* — acceptable for break-glass, and exactly the gap passkeys close. ADR-056 raised its stakes: on the tunnel and the LAN it is not a fallback but the whole identity, which is why those transports now carry E2E underneath it rather than "delegating confidentiality to the network".

### 3. URL fragment — a CHANNEL key, never a credential

`#k=<32-byte hex>` opens the E2E channel on a tunnel or LAN address. It is not an identity and grants nothing on its own. `#enroll=<token>` is the one link that IS a credential, and it is bounded to match: single-use, short TTL, `enroll` and nothing else.

**`#t=` is GONE (ADR-056).** The per-start 256-bit access token was a link that carried authority — a bookmark that authenticated — and every property it had (QR bootstrap, a shareable URL) is served by the channel key plus a real identity. There is **no compatibility lane**: bundles ship with the server, and a stale cached one gets typed refusals rather than a crash.

### 4. Tailnet identity — a username hint, and only that

Logged, surfaced by `/remote/auth-info`, and attached as the connection LABEL when `tailscale serve` supplied one — so `RemoteStatus.clientLogins` and every audit row still name who it was. It **admits nobody**. The unsolicited accept that used to authenticate a socket from the upgrade headers before any client frame is retired (ADR-056): a network fact is not a person, and device theft is precisely what ambient identity does not cover. `passkeyTailnetExempt` went with it — the exemption exempted from an admission that no longer exists.

One thing this simplified: `?intent=enroll` existed to decline that unsolicited accept, because at the tailnet origin it would otherwise win the race against a first device's `{auth, enrollToken}` frame and leave the link unspent. With no ambient accept there is no race, so the flag is inert; the web client still appends it (it costs nothing and keeps the URL byte-identical) and the server ignores it.

## Policy modes (`remoteAuthPolicy`)

Stored in `remote_config.auth_policy`, a **nullable** column where **NULL means AUTO**. AUTO is resolved per connection (`resolveAuthPolicy`): ≥1 enrolled credential ⇒ `passkey-always`, otherwise `password`. An explicitly stored value always wins. That is how "default once a credential is enrolled" holds without any code ever WRITING a policy behind the operator's back — enrolling the first passkey turns the mode on and revoking the last one turns it back off, and neither is a config mutation that could surprise someone reading the settings row.

| Mode | Behavior |
| ---- | -------- |
| AUTO (the `NULL` default) | `password` until the first passkey is enrolled, then `passkey-always`. |
| `passkey-always` | Every connection on a WebAuthn-capable origin performs the ceremony. The break-glass password is still accepted there while the toggle is on, and is accepted UNCONDITIONALLY on the origins where a passkey is impossible. |
| `password` | **Effective-only** — AUTO's zero-credential answer, never something an operator pins. No ceremony is owed (there is nothing to assert with); admission is a break-glass password, or an enrollment link. Pinning it would mean "keep accepting a password after I enrol a passkey", which is what `passwordBreakGlass` already says, on a knob that already exists. |
| `off` — **master switch** | All authentication disabled (owner decision: "if a user didn't want any auth, just disable all auth"). Hard requirements, all built: (1) explicit **host-anchor** opt-in with a typed confirmation — the operator types `disable remote authentication` verbatim before the write is enabled (`RemotePasskeySettings.tsx`); (2) a **persistent, non-dismissible warning banner** on the desktop settings surface *and* on every connected web client for as long as the mode is active. The web client keys that banner on `auth-response.authDisabled`, which the server sets on EVERY accept while the effective policy is `off` — keyed on the POLICY rather than on `method === 'none'`, so a client that presented a real credential is not silently spared the warning either. A mid-session flip needs no push: the auth-surface disconnect (4009) already makes every live client reconnect and read a fresh `auth-response`; (3) audit-log entries on enable/disable; (4) a startup log warning. Never reachable from a remote client — `remote:set-config` has no remote registration at all, which is the structural reason and not merely a capability check (a passkey connection DOES hold `admin`). Auth-mode `off` also **forces tier `off`** (ADR-054 decision 3). |

Two modes have been retired, in order. `passkey-for-grants` went with ADR-054: it was "legacy sign-in + `medium` tier" written as one knob, and the two axes are independent now (migration v12 rewrote stored rows to `legacy`). **`legacy` then went with ADR-056**, because what it named — the as-built ADR-039 stack — was the token and the ambient tailnet admission, and both are gone. Migration v13 rewrites stored `legacy` to NULL, i.e. back to AUTO, which resolves to `passkey-always` or `password` on the credential count: exactly the two things `legacy` was standing in for on either side of that line.

An **auth-surface change** — a write that moves any of `authPolicy` / `effectiveAuthPolicy` / `passwordBreakGlass` / `stepUpTier` / the three timing dials, *including* the AUTO flips caused by enrolling the first credential or revoking the last — does two things together (`authSurfaceChanged`): appends one `auth:policy-change` audit row, and drops every live remote client with close code **4009** so they re-authenticate under the new rules. The ACTOR is spared the disconnect, and is instead **re-snapshotted in place** (`resnapshotConnection`) — otherwise an operator flipping to `strong` would leave their own session as the one socket in the deployment that never expires. Clients treat 4009 as "reconnect and re-decide", never as a credential rejection.

**Rotating the LAN channel key is deliberately NOT an auth-surface change.** It moves which key a FUTURE handshake must present, not the admission rules for identities that already exist — so it audits as `auth:settings-change` and sweeps nobody. See §The LAN channel below.

### Close codes a client must not misread

| Code | Meaning | Client behavior |
| ---- | ------- | --------------- |
| **4009** auth surface changed | The RULES moved (policy, tier, break-glass, first enroll, last revoke). Not a verdict on this credential. | Reconnect immediately, no backoff. The fresh handshake decides what is now owed — possibly nothing. |
| **4010** session expired | `strong` tier only: the connection reached `sessionMaxAgeHours` measured from CONNECT and was cut, **sync stream included**. Not a rejection, not throttling. | Reconnect immediately, no backoff, and show the "Session expired — sign in again" notice (`SessionExpiredNotice`) so the sign-in screen is explained rather than mysterious. Latching `auth-rejected` here would strand the user on a screen whose only exit is a manual reload. |
| **4008** credentials changed | The password this socket authenticated with was rotated out from under it. | Re-prompt. **With one exception that is a success signal:** when this client is the one that called `authcfg:set-password`, the server drops it *before* the invoke response goes out — so the web adapter races the close against the response and reports the rotation as done (`api-adapter.ts`). A passkey-authenticated actor is not disconnected and gets the normal response. |
| 4006 throttled | Over the per-key failure budget. | Stop retrying; the reconnect backoff is suppressed. |
| **4004** E2E activation required/unavailable | The socket is on an E2E origin and sent something other than `e2e-activate` first (ADR-056), or tried to activate on an origin that has no channel key. | Not retryable as-is: open the channel first, or use the right address. |

## Capability grants

Every command in the registry **declares** a capability; undeclared commands fail to register (fail-closed — inverts the as-built denylist, whose failure mode was "forgot to blocklist ⇒ exposed"). Connections hold a grant set derived from auth method × policy × settings; the desktop renderer's connection holds all grants.

Capabilities: `chat`, `session-config`, `config`, `git`, `fs-read`, `shell`, `admin`, `enroll`, `host` (desktop shell only). `enroll` is ADR-052's addition and exists to be *separable* from `admin`: a one-time enrollment link must be able to register a credential and reach nothing else — not chat, not config, not git. Per-connection **identity** (method, login/credential nickname, connect time) is attached to every command — enabling the audit log and per-client subscriptions (retiring the collective-owner git-watch workaround).

**`admin` is EXACTLY the session-security area** since ADR-056: the `authcfg:*` and `webauthn:*` families, plus their host-anchor twin `remote:*`. The engine-vendor channels that used to carry it — `auth:*`, `account:*`, `shared-provider:*` writes, `vendor-auth:*`, `usage:refresh-prices` — declare `config` now. That is a rename, not a widening: they are desktop-only by their REGISTRATION (a channel is reachable over a transport iff it was registered for it), which is where the guarantee always actually lived. It also removes them from `PINNED_CAPABILITIES`, because `config` is in the base grant set and the pin table's one invariant is that every entry names a capability the base set does not hold.

### The registration sweep (S1b, 2026-08-17)

The owner ruling behind the headless arc is that **everything is changeable from the remote UI; host-PHYSICAL verbs are the only exception**. Until S1b a large part of the config surface was desktop-only *by omission* — registered in `session.ipc.ts` with no remote twin — so the sweep registered it deliberately instead. 37 channels, all of them declaring a capability the base grant set already holds (`config`, `git`, or `chat`), i.e. this is a real widening of what an ordinary authenticated connection reaches, and it is the ruling rather than an accident:

| Family | Capability | Channels |
| ------ | ---------- | -------- |
| `worktree:*` | `git` | create / status / remove / list |
| engine, vendor and opencode config (`config:save-slash-commands`, `config:{load,save}-engine-config`, `config:{load,save}-vendor-config`, `config:{load,save}-opencode-settings`, `config:read-opencode-native-raw`, `config:patch-opencode-native`) | `config` | 9 |
| `opencode-agents:*` CRUD | `config` (`generate` is `chat` — it spends model tokens) | 6 |
| `mcp:*` writes (`toggle`, `reconnect`, `set-servers`, `save-servers`, `remove-server`, `toggle-disabled`) | `config` | 6 |
| `proxy:test-connection`, `usage:refresh-prices` | `config` | 2 |
| `automation:*` | `config` | 10 |

Two structural facts make this reviewable rather than a leap of faith. **One declaration, two transports:** each channel is declared once, in `ipc/config-commands.ts` / `ipc/automation-commands.ts`, and both registrars spread the same object — the surfaces cannot drift about a capability, and a future desktop-only registration has to be written as one (pinned by `remote-channel-parity.test.ts`). **Nothing host-physical rides along:** `session:pick-folder`, `app:open-in-vscode` and `window:*` declare `host`, which no remote connection holds, and they have no remote registration either.

`automation:*` is the other half of the sweep — a PORT, not just a registration. Those ten channels were the last family on raw `ipcMain.handle`: no declared capability, no capability check, no audit row, no remote twin. They declare **`config`**, because an automation is host-side configuration (a stored prompt plus a cron expression under `~/.claude/ui/automation/`) and `admin` means exactly the session-security area. The "it runs prompts against the host on a timer" objection does not separate it from `session:send`, which runs a prompt against the host *right now* under `chat` — see §Posture: any authenticated remote client is already operator-level in effect. What the port buys is the enforcement the family never had: audited mutations, unaudited reads, and the mutation window on the `strong` tier. The seven mutating channels left `PINNED_CAPABILITIES` in the process, for the same reason `auth:*`/`account:*` did — a pin naming a grantable capability would break that table's one invariant.

`log-viewer:*` was ruled the opposite way, and stays pinned at `admin` with no registration anywhere: it is desktop WINDOW CHROME (open/minimize/maximize/close/theme of a `BrowserWindow`), host-physical in the same sense `window:*` is. A headless box has no log window to drive — it has the log file.

### The vendor-credential surface (S4, ADR-057)

The last family S1b deferred — native Claude OAuth, multi-account mutations, the per-vendor auth verbs, and the shared-provider writes — is registered on the remote transport too, from ONE shared declaration in `ipc/auth-commands.ts` that both `session.ipc.ts` and `remote-handlers.ts` spread (the same pattern as `config-commands.ts`). All `config`, so any authenticated connection reaches them.

| Family | Capability | Channels |
| ------ | ---------- | -------- |
| Native Claude OAuth (`auth:sign-in`, `auth:submit-code`, `auth:cancel`) | `config` | 3 |
| Multi-account mutations (`account:set-enabled`, `account:add`, `account:switch`, `account:delete`) | `config` | 4 (`account:get` was already on both transports) |
| Per-vendor auth (`vendor-auth:*` — probe / list-options / list-keys / set-key / oauth-authorize / oauth-callback / oauth-cancel / remove) | `config` | 8 |
| Shared-provider writes (`shared-provider:{save,remove,set-route,set-key,sync,disconnect,set-default}`) | `config` | 7 (the reads were already on both) |

These verbs are **flows, not just data**, and two properties keep them safe over remote:

- **Token material never crosses the wire.** `probe` / `list-keys` / `pi:auth-status` return `authState` / credential-kind / labels / booleans only; the mutations return void. No handler returns `access` / `refresh` / a key. The token EXCHANGE runs host-side (it holds the PKCE verifier and writes the credential stores); only the authorization CODE returns from the browser.
- **Consent happens in any browser on any device; the host-physical browser open does NOT fire for a remote caller.** `auth:sign-in` / `account:add` derive remote-vs-host from `connection.identity.method` (the "origin-derived flag") — the host's own in-process connection (`method: 'host'`, spelled `'desktop'` until the 2026-08-20 rename) opens the host browser exactly as before, any other method is remote and skips `shell.openExternal`, surfacing `manualUrl` for the remote UI to display; the code returns via `auth:submit-code`. For the Codex vault (`vendor-auth:oauth-callback`) the remote user pastes the whole callback URL and the host completes with the held verifier (see ADR-057). opencode's `auto` method — whose loopback lives inside the host's opencode server, unreachable from a remote browser — is refused from a remote caller with instructions to use the `code` method or the desktop; pi's Codex `auto` is not refused, because it completes via paste-back.

Reachability is unchanged in substance from the ADR-056 rename: these were already `config`, and were desktop-only by REGISTRATION; S4 adds the registration, deliberately.

Grant bundles (`grantsFor`) — **THREE outcomes since ADR-056, keyed on the METHOD alone**:

| Method | Bundle |
| ------ | ------ |
| `webauthn`, `password` | `FULL_REMOTE_GRANTS` — the base five plus `admin` and `enroll`, under **every** policy |
| `enroll-token` | `ENROLL_ONLY_GRANTS` — `enroll` and nothing else. It does not widen after a successful registration: the client re-runs the assertion on the same socket and comes back as `webauthn`, so the credential it just made is what buys it access |
| `none` (only reachable under `off`) | `AUTH_OFF_GRANTS` — the base five, deliberately NOT `admin`/`enroll`. Enrolling a credential while authentication is disabled would let any reachable client mint itself a permanent one, and without `admin` the settings session stays unreachable too |

The collapse matters twice over. **The policy is no longer an input at all**, which is the fix: the old `token` / `tailnet-identity` arms re-decided admission inside `grantsFor`, drifted from `ceremonyRequiredForAuth` within a week, and produced connections the server ACCEPTED and then refused on every single invoke. Admission is decided exactly once now, at the handshake, and `EMPTY_GRANTS` is not a state that can be spelled.

**The password gets `enroll`**, where under `legacy` it used to keep the base set. Withholding it was already theatre once the same connection held `admin`: `webauthn:mint-enroll-token` is an `admin` verb, so an admin-holding password client could always mint its own enrollment link and use it. The property that actually protects a fresh install — *the first device requires the anchor* — survives via the POLICY DEFAULT rather than via grant surgery: with zero credentials **and** no password provisioned, nothing can connect except an enrollment link, which is minted from the desktop or the console.

## The LAN channel (ADR-056 item C)

Plain-LAN connections carry E2E on a **persistent** key — `remote_config.lan_e2e_key`, 32 bytes hex — generated lazily on the first start that serves a non-loopback bind. Loopback-only runs (TLS mode, or an explicit `127.0.0.1` bind) mint nothing: a stored channel secret for an install that will only ever use `tailscale serve` is a secret with no channel behind it.

Persistent because a LAN bookmark has to survive a restart to be a bookmark at all — that is the difference from the tunnel key, which is ephemeral because its hostname is too. Rotatable because a persistent secret with no way to replace it is one leak away from permanent.

It is a **secret**, and never appears in `sanitizedRemoteConfig` / `authcfg:get`. Two dedicated verbs carry it, registered on BOTH transports (a headless box has no desktop pane to read a link from):

| Channel | Kind | Capability | Gate |
| ------- | ---- | ---------- | ---- |
| `authcfg:lan-link` | `query` | `admin` | **live settings session.** A `query` would classify `read` — free on every tier, like `authcfg:get` — so its membership of `AUTHCFG_CHANNELS` is the whole gate. What gates a verb in this namespace is what it DISCLOSES, not its kind, and this one discloses a live channel key. Answers `http://<ip>:<port>/remote#k=…`, with the ip:port from LIVE listener state (a listener on port 0 has a port nothing else knows). Typed `lan-link-unavailable` when the run serves no non-loopback bind |
| `authcfg:rotate-lan-key` | `command` | `admin` | **live settings session.** Mints a new key and returns the new link, so the actor's UI can render it immediately — a rotation whose new link the operator had to go and find is a rotation they would put off |

**The rotation NEVER STRANDS, by construction rather than by care.** `E2ECrypto.init` derives a connection's AES key at `e2e-activate` and the stored value is never read again for that socket, so every established channel keeps running on what it already derived: nobody is disconnected, and only a NEW handshake is measured against the new key. It is audited as `auth:settings-change` with **no 4009 sweep** — the admission rules for existing identities did not move, and sweeping would disconnect every live client to tell them something that does not apply to them. A client holding the retired link fails to decrypt the ack, never presents a credential, and dies on the pre-auth clock; the recovery anchor is the host — concretely, the **Access links card in the desktop Remote Access modal** (its LAN row shows the current link with no ceremony — on the desktop it reads `getStatus().lanUrl` rather than the gated `authcfg:lan-link` verb, and the host anchor would be exempt from the session gate even where it did call it — and renders the new one straight from the rotate response), or the server console on a headless box.

Rotation and `lan-link` stay OUT of `authcfg:apply`'s batch, on the same reasoning as `authcfg:set-password`: a channel key is not a config field.

**N6 — shared slot pool: RATIFIED as designed.** Terminals stay an ordered per-cwd pool shared by every surface (see §Terminal posture); naming a slot is not a capability, and the three gates run identically whichever surface opens it.

## Step-up tiers — post-login freshness (ADR-054)

Stored in `remote_config.step_up_tier`; default and fail-parse value `medium`. Auth-mode `off` **forces** tier `off` (`resolveStepUpTier`) — you cannot demand a ceremony from an identity that was never established, and gating a pty while unauthenticated model-mediated execution stands open is theatre. `RemoteConfig` exposes both the raw `stepUpTier` and the resolved `effectiveStepUpTier` for the same reason it exposes both policy values: a settings UI that re-derives the rule is how a displayed posture drifts from the enforced one.

| Tier | What it gates |
| ---- | ------------- |
| `strong` | Reads and the sync stream stay free. Every **mutating** command needs a presence proof inside its idle window — shell acts `shellGrantIdleMinutes` (default 10), all other mutations `stepUpMutationIdleMinutes` (default 60, 1–1440). The session itself has an absolute max-age, `sessionMaxAgeHours` (default 4, 1–**168**), measured from CONNECT and slid by nothing; at expiry the socket is cut with **4010**. |
| `medium` (default) | ADR-052's shipped behavior, named: step-up gates exactly the **terminal** (with the read/act split below) and the **remote-settings surface**. Everything else rides connection auth for the connection's lifetime. |
| `off` | Nothing else is gated post-login; the session lives until disconnect. The settings surface is the one exception (below). |

### The enforcement matrix

`classifyDispatch` puts every dispatch in exactly one class, and `evaluateStepUp` is a pure function of (tier × class × presence) — one table, read by the transport gate, by the service-layer backstop in `terminal-service.ts`, and by the tests. A verb cannot be a "read" at the transport and an "act" at the service, because only one place says which it is.

| Class | What lands here | `off` | `medium` | `strong` |
| ----- | --------------- | ----- | -------- | -------- |
| `read` | any `query` | free | free | free |
| `shell-read` | `terminal:attach` / `:detach` / `:pool` / `:resize` | free | armed ever | armed ever |
| `shell-act` | `terminal:create` / `:write` / `:kill` / `:kill-by-cwd`, and the `term-input` frame | free | act window | act window |
| `authcfg` | `authcfg:apply`, `authcfg:set-password` | **settings session** | **settings session** | **settings session** |
| `mutation` | any other `command` | free | free | mutation window |

Three properties of that table are load-bearing:

- **The settings area outranks the tier, including `off`.** ADR-054 decision 6 says these verbs are gated "regardless of tier" while decision 3 says tier `off` gates nothing; read literally the two collide, and the order is resolved in favour of decision 6. An operator choosing "don't nag me post-login" is choosing it for their chat and their shell, not for the surface that decides who may connect at all. Decision 3 is not weakened in substance: under auth-mode `off` a connection holds the as-built grant set and never `admin`, so it can never actually administer that surface. Note the ORDER precisely — the transport checks the session BEFORE capability dispatch, so such a connection meets `needs-settings-session` first and only hits `Permission denied` if it goes on to unlock. Both walls hold; the session one is simply in front.
- **Only acting refreshes, and only for an already-armed connection.** A shell act slides both windows; any other mutation slides the mutation window; reads slide nothing (the terminal panel re-asks `terminal:pool` on every window focus, so a refreshing read would let a tab the operator merely left open renew its own grant forever). An UNARMED connection refreshes nothing at all — refreshes EXTEND a proof and must never create one. **Nothing refreshes the settings session:** it is a fixed-length mode, and a sliding one would be the ambient administering authority again, wearing a countdown.
- **Fail-closed on an unclassified shell verb.** A `shell`-capability channel in neither verb set is treated as ACTING. `shell-verb-sets-cover-the-registry` pins that nobody relies on that fallback in practice.

### Arm-on-auth (kills the double ceremony)

A login that *is* a presence proof arms at accept: a **passkey ceremony** — handshake assertion or the enroll→webauthn upgrade — arms everything its tier would later gate, fresh (`armPresence`). The one weaker login left arms nothing and meets the step-up as its FIRST presence proof: the break-glass password. **The password never arms at login** — its proof is client-cacheable, so it authenticates the browser rather than the human — but it remains a valid step-up FACTOR, including for the settings area (owner-ratified). What a password may never do is reach the `off` switch, which is host-anchor only on every transport.

Two refusals guard the arming path:

- **Narrow-grant sockets are never widened by arming.** An `enroll`-only socket (a one-time "add this device" link) cannot be handed `shell` by the tier-`off` waiver *or* by a completed step-up. Keyed on the GRANT SET (`holdsBaseRemoteSurface`), not on a method denylist, so a future narrow-grant method is excluded by construction. ADR-052's invariant — a leaked link can add a device but cannot read a conversation — stands unchanged.
- **The tier-`off` waiver is a capability grant, not a proof.** Admitting a connection under tier `off` sets `armedEver` and confers `shell` but writes **no windows** (`armedByWaiver`), so it cannot buy the settings-area gate for free. Flipping the tier back off `off` UNDOES it: the `shell` capability is withdrawn, `armedEver` and the mutation window are cleared, and attachments are dropped with detach-reason `grant-expired`.

### Grant decay (sudo semantics)

- Idle means *no shell-bearing ACTS* for `shellGrantIdleMinutes`. Reading chat does not keep a shell grant warm, and **neither does a shell READ** — see the refresh discipline above.
- On expiry the next shell ACT returns `needs-step-up`; the client runs a **fresh passkey ceremony** — `step-up-challenge-request` → sign → `step-up {assertion}` — with the password as fallback where passkeys are unavailable or break-glass is on. The step-up challenge is bound to its own `step-up` KIND, so a handshake challenge cannot be replayed into a grant (nor the reverse), and both factors spend the SAME per-key failure budget: an assertion brute force gets no fresh allowance for arriving in a different frame field.
- **Decay no longer strips the `shell` capability or drops attachments.** That is the read/act split: a decayed window refuses acts and leaves reads alone. The capability is now withdrawn only by the desktop toggle (a real revocation of authority) and by the tier-`off` waiver being undone.
- **The terminal toggle withdraws the SHELL, not the ceremony.** Under ADR-052 a step-up requested while "Allow remote terminal" was off was refused outright with `terminal-disabled` / `retryable: false` — correct when step-up existed for exactly one thing. Under ADR-054 the same ceremony is the only way to satisfy the settings gate (every tier) and the strong tier's mutation window, and the terminal ships OFF, so that refusal locked an operator out of their own remote-settings surface in the DEFAULT configuration and took the headless bootstrap chain with it. The ceremony now runs, `armPresence` withholds the `shell` capability (and its window) while still recording the presence proof, and every terminal verb stays refused by the two independent toggle checks it always had — the transport gate and the service-layer backstop.
- **Under auth-mode `off` nothing is gated**, tier included (decision 3). ADR-052's "step-up still demands a factor under `off`" no longer holds and was superseded deliberately — the banners, typed opt-in, startup warning and audit rows carry that posture instead.
- Enforced **server-side** (grant state + timers). Client credential caching is irrelevant to enforcement — this is the property that makes the whole scheme real.

### The client side of a refusal

`needs-step-up` is an answer about the CONNECTION's freshness, not about the verb, so exactly one place on the web client knows how to cure it: `web/step-up-gate.ts`, installed on `RemoteConnection.invoke` (`setInvokeGate`). It forwards every call, and on a `needs-step-up` refusal it opens ONE ceremony for however many calls are waiting, then retries each **once**; a dismissed ceremony rethrows the server's original refusal so call sites that already understand it (the terminal panel's inline prompt) keep working unchanged. A second refusal after a *successful* ceremony is not a freshness problem and is not retried again. Concurrent refusals join the same ceremony — beyond avoiding a prompt storm, concurrent `startAuthentication()` calls would race the server's single-use, connection-bound challenge. The ceremony UI itself is ONE component (`shared/StepUpPrompt.tsx`) rendered by both the terminal panel and the generic modal, so the two refusal codes that move the prompt between factors cannot behave differently in the two places. The desktop renderer installs no gate at all — its connection is exempt from the whole table and can never be answered `needs-step-up`.

## The host anchor & the `authcfg:*` surface (ADR-054 decision 6)

"Desktop-only" was standing in for *"a surface that requires being on the host"* — which the headless deployment (no desktop at all) forces us to name properly. The line is drawn between two kinds of settings, not between two transports:

- **Auth-DISABLING operations** — the `off` master switch, and anything else that turns authentication off — are **host-anchor only, forever**: the desktop renderer today, the server's own console/config file (reached over SSH) on a headless box. Never the web, not even behind a fresh ceremony, because a stolen stepped-up session must not be able to disable authentication. That writer stays in `remote:set-config`, which has **no remote registration at all** — a structural guarantee, not a capability check. Clearing the break-glass password (`remote:clear-password`) and the transport settings (port, bind host, `tailscale serve`, the `allowTerminal` toggle) sit on the same side: a remote client must never take over the transport it is talking through.
- **Routine remote-access settings** — step-up tier, all three freshness DIALS (idle re-check, terminal re-check, session max-age), the two admission toggles (break-glass, tailnet exemption), auth-mode changes among the NON-`off` modes, password rotation, audit retention, and credential list/rename/revoke — are **web-reachable inside a settings-editing session** (below). The dials were host-anchor-only as first shipped, as a compensating restriction for an *ambient* administering capability; the 2026-08-16 amendment removed the ambience, and with it the reason.

The routine set gets its own namespace so the structural guard survives intact.

### The settings-editing session (amendment, 2026-08-16)

As first shipped, each `authcfg` mutation checked the 60-minute mutation window. That left administering as a long-lived **ambient** capability — invisible while held, held by any connection that had recently done anything at all — and it is why the timing dials had to stay desktop-only as a compensating restriction. Replaced by an explicit bounded mode:

- The pane is **read-only by default**. One "Edit settings" action; on the web it runs the standard step-up ceremony carrying `intent: 'settings'` (an additive optional field on the `step-up` frame, so an older bundle stays byte-compatible). On success the server marks THAT connection as holding a live settings session, TTL **5 minutes** (`SETTINGS_SESSION_TTL_MS`).
- Deliberately **server-side connection state, not a wire token**: the connection is already authenticated and the ceremony just ran on it, so a bearer string would add leakable surface without adding proof.
- A settings-intent step-up **also does ordinary arming** — a step-up is a step-up, and splitting "which proof counts for what" by intent would be a second rule about one ceremony. The intent selects a CONSEQUENCE of a proof the server verifies either way, so asserting it on a ceremony that fails buys nothing.
- Revoked by `authcfg:end`, by disconnect, or by the TTL — **checked lazily at dispatch**, because a bounded mode nobody is watching needs no timer and a timer would be a second thing that has to agree with the deadline. Expiry writes no audit row (nothing happened).
- The `host` connection is **exempt**, as everywhere: it IS the host anchor, so its editor unlocks with no ceremony and has no TTL.

| Channel | Kind | Capability | Gate |
| ------- | ---- | ---------- | ---- |
| `authcfg:get` | `query` | `admin` | **none** — the pane's default state IS the read, and demanding an unlock to display the current settings would put the ceremony in front of its own explanation. Answers the same sanitized `RemoteConfig` object `remote:get-config` does (one sanitizer, `services/remote-config-view.ts`), so salt / hash / KDF params never cross the wire. |
| `authcfg:apply` | `command` | `admin` | **live session.** The editor's Save: the whole edited set as ONE batch — every field validated before any is written, then one `auth:policy-change` row carrying the diff, one 4009 re-admission sweep (except-actor, actor re-snapshots in place). **Every auth-surface field re-admits exactly like the tier does** — the three timing dials and the two admission toggles included. The mutation window and the max-age are snapshotted per connection at authentication, so a change that skipped the sweep would leave live sockets running on the old numbers; the terminal's own window is re-read at each arming, so the sweep there clears an already-armed deadline rather than un-stranding a snapshot. One operator action, one audit row naming everything that moved, one sweep. Retention alone does not sweep — how long the trail is kept does not change who may connect. Refuses an `off` auth-mode with `auth-off-is-host-anchor-only`. A zero-change apply succeeds, writes nothing and drops nobody. |
| `authcfg:set-password` | `command` | `admin` | **live session.** Its 4008 semantics are unchanged. Kept out of the batch because a password is not a config field: write-only, never read back, and its disconnect behavior is nothing like a settings diff's. |
| `authcfg:end` | `command` | `admin` | **none** — it only ever gives authority back. Audited as `auth:settings-session` (an end is a session event, not a settings write). Gating a revocation is backwards twice over: Cancel and pane-close must work unconditionally, and under `strong` an unclassified `command` would demand the mutation window, so an operator whose window had lapsed could open an editor and be refused permission to close it. Idempotent: calling it with nothing open is a no-op success. |

`authcfg:set-tier` / `:set-auth-mode` / `:set-retention` are **retired** — `apply` subsumes them, and one Save is one audit row and one sweep rather than up to three of each.

Both transports register all four (`authcfg.ipc.ts` + `remote-handlers.ts`), so the capability/kind declaration is a single reviewed fact; the bodies assert the session **again** through the same table, so a future transport that forgets the gate still cannot rewrite the auth surface with the editor locked. Two pins keep the namespace honest: every registered `authcfg:*` channel is in exactly one classifier set (`AUTHCFG_CHANNELS` gated, `AUTHCFG_FREE_CHANNELS` free) — never both, never neither.

**The refusal is typed.** A locked editor answers `needs-settings-session`, not `needs-step-up`, and the distinction is the point: the web client's generic step-up gate cures `needs-step-up` ambiently (one ceremony, one retry) and must NOT do that here. A stale pane firing a save would otherwise raise a biometric prompt nobody asked for, and a tap would silently re-enter the mode. The client's contract for this code is: do not retry, re-lock the editor, let the operator press Edit again.

Client side, the pane has three states (`SessionSecuritySettings`): a read-only **summary** of the six facts with one "Edit settings" button and no inputs mounted at all; the **unlock** ceremony (web only — the desktop flips straight through); and **edit in place**, with a countdown pill ticking from the server's deadline, and Save / Cancel. Nothing is written until Save, which sends one batch and then closes the session; Cancel and unmount close it too. A session that lapses mid-edit re-locks to the summary with a notice and **keeps the draft**, so unlocking again and pressing Save recovers the whole edit — losing an operator's work to a five-minute timer would teach them to rush, which is the opposite of what a deliberate mode is for. The `off` option is offered only on the desktop, inside the edit state, behind its typed confirmation, and it stages like every other field so "changes apply together" stays true of the one change that matters most.

### Headless bootstrap chain (owner-ratified)

A headless install has no desktop renderer, so "the first passkey comes from the desktop" needs a second answer. The chain, end to end:

1. **First boot prints a one-time enrollment URL on the console.** Same mint as the desktop's "Add device": single-use, short TTL, and necessarily at the tailnet HTTPS name, because that hostname IS the RP ID the credential will bind to.
2. **The first passkey ceremony signs the device in; opening the settings editor then costs one deliberate unlock.** Arm-on-auth still means that device lands armed, so nothing else nags it — but administering is a bounded mode now rather than an ambient window, so the editor asks once when it is opened (amendment, 2026-08-16). One extra tap, and the rest of the chain is unchanged.
3. **`authcfg:*` is then usable for day-to-day administration**, including `authcfg:set-password` to provision a break-glass credential if the operator wants one, and `authcfg:lan-link` / `:rotate-lan-key` for the LAN channel. Enrolling that first credential also flips AUTO from `password` to `passkey-always` with no config write.
4. **Password-only headless** stays possible for an operator who does not want passkeys: provision the credential through the host's own config/CLI (the host anchor) — concretely, **`claudeui-server set-password`**, which reads the secret from stdin (echo off and asked twice on a terminal, one unconfirmed line on a pipe, never from argv or the environment). What it SHARES with the other two password writers is the credential itself and its trail: `provisionPassword` (the strength rule, the salt, the scrypt parameters and the stored hash) and `auditSettingsChange` (the `auth:settings-change` row). It does not share their orchestration — the console and the desktop host anchor both go through `provisionBreakGlassPassword`, which attributes the row to the host anchor (`method: 'host'`, labelled `server-console` or `desktop-renderer` — passed as its `actor`) and names the VERB in `detail`, while `authcfg:set-password` composes the same two pieces under the connection's own identity. **Only the SUCCESS row is common** (accepted, owner-ratified 2026-08-20): a REFUSED attempt (too short, wrong session) leaves a dispatch error row on the web path and nothing at all on the desktop/console paths, which are raw host-anchor calls outside the command registry. The asymmetry mirrors the trust model — the registry audits remote actors' attempts; the host anchor is trusted by definition, so auditing its typos is observability, not security. The web client then authenticates with the credential as it does on the desktop-backed deployment. A password login arms nothing, so the first settings write meets a step-up — which the password itself may satisfy. The console **provisions but never clears**: turning break-glass off is `passwordBreakGlass: false` in Settings, something you can only want once you can already get in.
5. **All passkeys lost ⇒ console re-mint.** The recovery is the same as step 1: re-mint the one-time enrollment URL from the server console. There is deliberately no network-reachable recovery, because a network-reachable recovery is a network-reachable bypass.

**What ADR-056 sharpened here.** The chain's first link used to have an ambient shortcut behind it: on a `tailscale serve` box the owner's own browser was admitted from the upgrade headers, so "nothing can connect yet" was not quite true. It is now. **With zero credentials and no password provisioned, a fresh install admits nobody** — `/remote/auth-info` legitimately advertises an EMPTY method list, which is more honest than naming a method that would be refused — and the console-printed enrollment URL is the only way in. That is what makes step 1 a real bootstrap rather than a convenience, and it is the same property that lets the password carry `enroll` (§Capability grants) without weakening the first-device rule.

## Audit

Append-only SQLite (typed repo enforces append-only):

- **Commands:** `{ts, connectionId, identity, capability, commandType, sessionId?, outcome}`.
- **The identity is two columns, and they answer different questions.** `method` is the `IdentityMethod` the connection was admitted under — `password`, `webauthn`, `enroll-token`, `none`, or **`host`** for the host's own in-process, fully-trusted surface (the one identity that presented no credential because it never crossed a wire). `label` is WHO/WHICH within that: a tailnet login, a passkey nickname, or — for `host` — **which host surface**, `desktop-renderer` or `server-console`. The `host` method was called `desktop` until 2026-08-20; since ADR-058 `src/main` and `src/server` are sibling HOSTS, so on a headless box that value named a renderer the machine does not have. Both columns are TEXT and nothing reads them back for a decision, so the rename carries **no migration and no epoch marker** — pre-release, existing local rows keep whatever they say. Not to be confused with the registry's `Transport`, whose `desktop` member is a different axis: which WIRE served the invoke, not who was on the far end.
- **Auth events:** successes/failures, step-ups, policy changes (master-switch flips prominently included), credential enroll/revoke. ADR-052 adds three `auth:*` channels, written through `appendAuditLog` with the same row shape: `auth:webauthn-assert` (every handshake, enroll-upgrade and step-up assertion, `outcome` ok/error), `auth:enroll-token` (a one-time link consumed, or refused), and `auth:policy-change` (one row per auth-surface change, from either the config path or the credential path — `auditAuthPolicyChange` is the single writer so an audit reader never has to know which path produced it). Credential enroll/revoke additionally ride the ordinary `command`-kind dispatch rows for `webauthn:*`.
- The `capability` column is TEXT, not an enum, and these `auth:*` rows carry the capability the event is ABOUT (`admin` for handshake/policy events, `enroll` for enrollment-token events) rather than one the connection held at the time — the connection frequently held nothing. Recorded here because it is a convention a reader has to know; it is not enforced anywhere. A **step-up** row names what the ceremony actually armed, which since ADR-054 is not always the shell: `shell` when the terminal toggle was on, `admin` when it was off and only the mutation/settings window was armed. Hardcoding `shell` there would have told a forensic reader that a session held a shell it was never given.
- **`detail` (migration v12):** a nullable TEXT column carrying explicit INTENT on auth rows — "passkey login accepted; conferred admin+enroll", "shell grant armed via step-up", "effective policy password→passkey-always via first enrollment", "break-glass password rotated via `authcfg:set-password`", "session expired (strong tier max-age 4h)". Command rows leave it NULL. It exists so a reader does not have to know the `capability` convention above to understand what happened. ADR-054 adds three channels alongside the ADR-052 three: `auth:settings-change` (a routine settings write that is NOT an admission-rule change, so it triggers no 4009 — retention and password rotation), `auth:session-expired` (the strong-tier cut), and `auth:settings-session` (an editor OPENED — detail naming the factor — or explicitly ENDED). A TTL expiry writes no row: nothing happened.
- **Terminal sessions:** spawn/attach/detach/exit with identity, cwd, duration — **never PTY content or keystrokes** (they capture secrets).
- **Voice captures (phase 5 S3):** `voice:start` / `voice:stop` are ordinary `chat`/`command` dispatch rows, so who opened a microphone on which session, and when, is in the trail — **never the audio, and never the transcript**. Audio is keystrokes by the same reasoning PTY content is: it rides the `voice-audio` lane frame (client→server) and targeted `stream-ev` frames (server→client), neither of which is ringed or logged. The frames themselves are unaudited for the same reason `term-input` is — a row per 150 ms batch would bury every command that matters.
- **Retention: a uniform moving purge** (ADR-054 decision 5), `auditRetentionDays` — default **365**, floor **30**, clamped on both read and write so no call path can purge below it. It runs on DB open and then on a timer (`unref`'d, best-effort — a desktop app can stay open for weeks, and a window that only advances on restart is not a window), following the usage-prune pattern. *Uniform* means auth rows purge on the same window as command rows: the owner considered an auth-rows-forever exception and declined it. The floor is what stops a session under investigation from erasing the trail of its own investigation in one call.

## Terminal posture

Off by default; a desktop-side "Allow remote terminal" toggle arms the `shell` capability at all. Using it requires the (decaying) `shell` grant + step-up per above.

**The read/act split (ADR-054 decision 4, applies in `medium` AND `strong`).** Owner-designed, borrowing the strong tier's principle into the terminal itself:

- **Reads stay free after decay.** An attached view keeps streaming (a `logcat` left running keeps running), `terminal:pool` keeps answering, re-`attach`/`detach` to *watch* costs nothing, and `resize` is read-class — it writes SIGWINCH and changes display geometry but cannot execute, and a watched view must survive a window resize.
- **Acts demand freshness.** `terminal:create`, input (`terminal:write` / `term-input`), `terminal:kill`, `terminal:kill-by-cwd`. The keystroke after an idle gap is what prompts.
- **First access ever still costs one arming proof.** A connection that has never proved presence (and was not armed by a passkey login) cannot attach or read terminals at all — scrollback and the operator's live-shell inventory are sensitive. One proof unlocks reads for the socket's lifetime and acts for the decay window.
- The split is an **explicit verb set**, not a derivation from `kind`: `terminal:attach`/`:detach` are declared `command` so the audit trail carries terminal lifecycle (§Audit requires spawn/attach/detach/exit), yet they are reads in the freshness sense — and `terminal:pool` is a `query` that is nonetheless a shell read. Deriving from `kind` would be wrong in exactly the cases that matter, and "relabel attach as a query" would silently drop it from the audit log.

Clients see this third state through `TerminalAvailability.readsAllowed`, alongside `granted` (which kept its ADR-052 meaning, "may I ACT?"). Both answer for the CAPABILITY as well as the presence proof: the toggle going off strips `shell` and deliberately leaves `armedEver` standing, so a connection that lived through an off→on cycle — or that stepped up while the toggle was off — is armed but holds no shell, and must be shown the wall rather than a "Watching" terminal whose every read the registry refuses. One ceremony recovers it. When reads are allowed but the act window has decayed the web panel renders the terminal **attached and streaming, read-only**, badged "Watching", rather than a step-up wall in front of shells the connection is entitled to see. The server refuses a stale `term-input` frame **silently** — an error would be an oracle for which terminals exist — so the client cannot learn from a dropped frame and holds the first keystroke back itself, opening one ceremony and DROPPING the key (buffering it would replay what was typed at a shell whose state has moved on; the user retypes). `grant-expired` is no longer emitted as a detach reason by decay, but is live again for a WITHDRAWN tier-`off` waiver. Multi-attach doubles as an audit feature — the owner can watch any remote shell live from the desktop. Terminals are an ordered per-cwd pool ([sync-core.md](sync-core.md) §Terminal), so an open names a SLOT and may resolve to a pty another surface spawned: that changes which pty an open lands on, never who may open one. Naming a slot is not a capability — `terminal:create`/`attach` run the same three gates either way, so an unauthenticated or un-stepped-up client cannot reach the operator's shell by guessing an index. The index is nonetheless attacker-controlled data on a granted socket, and claiming a slot pads the pool array up to it, so it is **bounded** (`MAX_POOL_INDEX`, 64) and refused past that with the malformed-index error: without the clamp a single `terminal:create(cwd, 2**31-1)` frame hangs or OOMs the main process before any pty is spawned — availability, not authority. `terminal:attach` is registered for the desktop transport too (it is how a desktop tab replays a pty it did not spawn) and is audited there on the same `command`-kind dispatch. `terminal:pool(cwd)` — the read that tells a client whether reopening a slot would RE-ATTACH — declares `shell` rather than `config`: `terminal:availability` must be answerable before the grant exists (it is the "may I?"), but an inventory of the operator's live shells is a fact ABOUT those shells and stays behind all three gates. It is a `query` (no lifecycle moves, nothing to audit) and returns slot numbers only, never pty ids. This supersedes the audit-era `terminal:*` denylist and ADR-048 Decision 5 (terminal-on-mobile declined), both of which were scoped to the pre-SyncCore trust model.

## Enrollment & recovery

- **The first device requires the host anchor, BY CONSTRUCTION — but the construction MOVED (ADR-056).** It used to be a grant carve-out: under effective-`legacy` a password connection held the base set and therefore no `enroll`, so the server refused `webauthn:register-*` on it. That was already theatre, because the same connection held `admin` and `webauthn:mint-enroll-token` is an `admin` verb — it could always mint its own link and use it. The property now rests on the POLICY DEFAULT instead, where it is real: with zero credentials **and** no password provisioned, nothing can connect at all, so the first passkey necessarily comes from the desktop's QR / copied link or from the console-printed URL on a headless first boot. A password that exists was provisioned by somebody who was already on the host.
- **Inline self-enroll works from any password connection ON AN ORIGIN THAT CAN BIND.** A break-glass password carries `admin` + `enroll`, so the web client's post-password offer ("Enroll this device") registers on the connection it is already on. The offer is non-blocking and its dismissal is remembered per device; when the server refuses it, the client renders the host guidance above rather than an error.
- **The offer's origin gate is the SERVER's, not the browser's.** The accept (`auth-response`) carries `webauthnCapableOrigin` — present exactly when `resolveWebauthnOrigin(Host, tlsServe)` returned an RP ID for that socket, i.e. the same value the password and ceremony gates were decided from — and the client offers only when it is set. A browser can observe nothing better than "am I a secure context", which is strictly weaker: **the Cloudflare tunnel is HTTPS**, so it passes every browser-side test while its RP ID is an ephemeral `*.trycloudflare.com` name the next link does not share, and offering there proposes a ceremony that cannot outlive the tunnel. The resulting matrix is tailnet ⇒ offered (including the first web login with nothing enrolled, where the refusal itself is the teaching), localhost dev ⇒ offered, tunnel ⇒ never, LAN ⇒ never. The browser check *survives* as a second condition rather than the origin one, because `resolveWebauthnOrigin` reads only the name: `http://<tailnet-dns>:<port>` — the same machine reached over its plain-HTTP LAN listener — is a capable HOST on a page that is not a secure context. The field is a UI signal and never an authorization one; what a ceremony may actually do is still decided at `webauthn:*` time from the connection's `webauthnOrigin`. ABSENT rather than `false` when the origin cannot bind, so a client that predates it reads "not capable" and withholds an offer instead of inventing one.
- **More devices:** "Add device" from any `admin`-capable client mints a one-time token. Minting requires `tailscale serve` to be UP and fails with `enroll-unavailable` otherwise — not as a convenience check: the URL's hostname IS the RP ID the credential binds to, so a link pointing at a LAN IP or a tunnel would produce either a failed ceremony or a credential bound to a name that will not exist tomorrow. **Enrollment therefore always happens at the tailnet origin.** Tokens are single-use with a short TTL and live in an in-memory map, so a process restart invalidates them; each UI action mints a fresh one.
- **The enrollment socket never widens silently.** A `#enroll=<token>` link authenticates an `enroll`-only connection; after `webauthn:register-verify` succeeds the client runs the assertion ceremony *on the same socket* and is upgraded in place to `webauthn` (same connection id, one thread in the audit log). A registration that half-completed leaves an `enroll`-only socket, not an admin one.
- **`?intent=enroll` is now INERT, and the reason it existed is worth keeping.** Enrollment can only happen at the tailnet origin — that hostname *is* the RP ID — and that was exactly the origin where `tailscale serve` attached an owner identity the server accepted at CONNECTION time, before any client frame. With nothing enrolled, no ceremony was owed, so the unsolicited accept always won the race and a first device's link went unspent with no biometric ever requested. The flag declined that accept for one socket. ADR-056 retired ambient admission outright, so there is no accept left to decline and no race left to lose. The web client still appends the (non-secret) parameter — it costs nothing and keeps the enrollment URL byte-identical — and the server ignores it; the **token never rode the query string** either way.
- **A failed UPGRADE keeps that socket.** The server does not close on a refused upgrade assertion, and the client must not either: the token was consumed to authenticate the socket, so reconnecting would present a burned credential — a dead end reached *with* a perfectly good passkey already registered. The retry re-runs the assertion only; asking for registration options again would hand the authenticator an `excludeCredentials` list containing the key it just made. Once the upgrade lands, the client strips `#enroll=` from the address bar so a reload or a bookmark cannot re-present a spent secret, and a definitively refused link offers "sign in normally" rather than dead-ending.
- **The desktop renderer never runs a ceremony.** It loads from `file://` (or the vite dev origin), so it has no RP ID and its connection's `webauthnOrigin` is null. Only the four management verbs are registered for the desktop transport (`webauthn.ipc.ts`); the two register verbs are remote-only.
- **Management:** list credentials (nickname, created, last-used, `backedUp`), rename inline, revoke individually. Revoking the LAST credential is refused (`last-credential-lockout`) only when the policy is *explicitly* `passkey-always` and no usable break-glass password exists — under AUTO it simply reverts to `password`, which is what AUTO means. The guard demands the password actually EXISTS, not merely that the toggle is on.
- **Recovery:** all passkeys lost ⇒ re-enroll from local desktop access or the server console (see the headless bootstrap chain above); break-glass password if enabled. There is deliberately no network-reachable recovery path.

## Implementation notes

- Use **`@simplewebauthn/server`** (+ `@simplewebauthn/browser`) — mature, popular, TypeScript, no native deps; never hand-roll CBOR/COSE (supply-chain and correctness posture).
- WebAuthn requires a secure context; `localhost` qualifies for development.
- **Client channel family:** `webauthn:register-options`, `webauthn:register-verify` (capability `enroll`, remote transport only), `webauthn:credentials`, `webauthn:rename`, `webauthn:revoke`, `webauthn:mint-enroll-token` (capability `admin`, both transports), plus the five `authcfg:*` verbs above (capability `admin`, both transports). The web `api-adapter` mirrors all of them per ADR-008; the desktop preload mirrors the four passkey-management verbs that exist there, rejects the two ceremony verbs locally, and wires all four `authcfg` writes for real. The web client's `getRemoteConfig()` resolves to `authcfg:get` while the desktop's resolves to `remote:get-config` — one `ClaudeAPI` signature, two writers, which is what lets the settings components be shared and branch only on WRITES (`remote-settings-transport.ts`).
- **Every ceremony starts from a tap.** `navigator.credentials.get()` needs a transient user activation on Safari/iOS, so a `passkey-required` answer on a page nobody has touched only ever renders the one-tap screen. Within a tap the client *auto-continues*: the socket it needs may be down, so the tap connects, and the `passkey-required` that comes back on the fresh socket starts the ceremony without a second tap. That arming lives and dies with the attempt — any settled failure (socket lost, 120 s budget spent, prompt dismissed) returns the user to the tap screen rather than leaving a later reconnect free to raise a biometric prompt nobody asked for.
