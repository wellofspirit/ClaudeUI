# Persistence & settings

Part of [architecture/](README.md).

## Persistence model

Two planes of on-disk state (ADR-020):

- **Config = plain-text files** (hand-editable, no private copies of engine-native config):
  - `~/.claude/ui/settings.json` — APP-tier settings (plane ①).
  - `~/.claude/ui/engines/<id>.json` / `vendors/<id>.json` — launch params: sandbox/proxy, endpoint/modelOverride, dispatch config (plane ③).
  - `~/.claude/ui/automode.json` — the engine-SHARED classifier trust lists (`trustedDomains` / `trustedRegistries` / `protectedPatterns`, ADR-065). OpencodeSession and PiSession derive them into the judge environment at session start; Claude runs cli.js's own classifier and cannot consume them. An empty list is an absent key. A read-time, run-once migration (`ui-config.migrateSharedTrustLists()`) unioned the two engines' old `autoMode` lists into it and stripped them from the engine files. The same file holds the other shared judge switches (`readOnlyBypass`, `blockHoldSeconds`, ADR-084/091) and `captureJudgeReplies` (diagnostics, stored only as `true`, read per judge call).
  - `~/.claude/ui/logs/judge/YYYYMMDD.jsonl` — **judge-reply capture**, written only while `captureJudgeReplies` is on (Settings › Trust & protection › "Record judge replies for diagnostics"; `core/automode/judge-capture.ts`). One record per call ClaudeUI's HTTP judge transport (ADR-081: opencode, pi and cross-engine dispatch targets; never Claude Code's own classifier) sent a request for, success or failure: `{kind:"call", ts, durationMs, engine, routingId, sessionId, route, model, wire, stage, maxTokens, maxChars, stopSequences, systemHash, user, outcome: "ok"|"error"|"aborted", error?, status?, finish?, usage?, text?, raw, reasoning?, reasoningTruncated?}`. `raw` is every visible delta in arrival order, including the text the verdict path discards (the overflowing delta of a `judge output exceeded its budget` failure, the opening delta(s) of an off-format stage-1 reply abandoned by its `allowedPrefixes` — ADR-109 — anything after the stop cut); `text` is what the classifier received. The system prompt is tens of KB, so it is written once per hash per day file as `{kind:"system", ts, systemHash, system}` before the first call that names it (`systemHash` = `judgeCacheKey`). The files hold the judged transcript excerpts, carry no credential, account id or header, stay on this machine, and are pruned after 14 days (once per process, on the first write). Writes are async and serialized through one queue; a failed write logs one warning and never touches a verdict. Reasoning text is recorded only when the stream already carried it (capped at 256 KiB); no request is ever changed to obtain it.
  - Claude's own `settings.json` / `.mcp.json` and opencode's `opencode.jsonc` / agent files — edited **in place**, never copied (plane ②; ADR-009, ADR-028/031).
- **Operational/derived = SQLite** (`~/.claude/ui/operational.db`, WAL, `user_version` migrations): `session_meta` (per-session engine+model), `account` (metadata), `usage_event` / `usage_window_sample` / `usage_bucket` (metering — the ledger, its window samples, and the hourly rollup that outlives the ledger's 90-day retention; a dispatched turn is a `usage_event` row with `origin = 'dispatch'`), plus `dispatch_target` (the X-Agent ledger, ADR-105, v35: one row per dispatch target — its harness session id, owning parent session, working directory, model, restriction and state — which resumes the target after its parent restarts and is what the history lists and block usage consult to skip the target's hidden harness session; `hand_back` (v36) says whether the target's thread has the report tool; `owner_pid INTEGER` and `owner_boot TEXT` (v39) name the ClaudeUI instance — process id plus a random per-boot id — that runs a `running` target, NULL for any other state and for rows written before v39, and the boot pass interrupts a `running` row only when its owner is gone, so a second instance sharing the database leaves it alone), plus `dispatch_report` (v36: how each run of an X-Agent ended — the report it handed back through `hand_back`, flagged or not by the review of its own judge, with the warning or note that review put above it in `warning` (v38), a withhold, a stop, a failure — keyed by the target and the run's number, with the call that launched the run in `tool_use_id`; read back for the X-Agent's cards on reload), plus `session_inbox` (ADR-104's persistent inbox of items held for a session that is not live; v37 adds `report_run`, the run an X-Agent result in the inbox reports, so the flush that delivers it stamps that run's `dispatch_report.delivered_at`), plus the remote layer's `remote_config`, `webauthn_credential` and the append-only `audit_log`. `src/core/services/db.ts` owns the migrations and the typed repositories; it reaches the engine only through the driver seam below.
- **Credentials = file-based** per-account dirs (ADR-015) — never in the DB.

### The SQLite driver seam (ADR-058)

`db.ts` no longer imports `better-sqlite3` — or any engine. `src/core/services/sqlite-driver.ts` declares a neutral `SqliteDriver` (`open(filename, {readonly?, fileMustExist?})` → a handle with `exec` / `pragma` / `prepare` / `close`), and `src/core/services/sqlite/` holds the three adapters: `better-sqlite3-driver.ts` (**the only importer of the native module**), `bun-sqlite-driver.ts` and `node-sqlite-driver.ts` — the last two taking their engine INJECTED by the entrypoint, because `bun build` hoists a static engine import even down a branch that never runs.

**Selection is explicit and belongs to the entrypoint; nothing sniffs the runtime.** `src/main/index.ts` installs `betterSqlite3Driver()`, `src/server/main.ts` installs `bun:sqlite` under bun and `node:sqlite` under node (an ENTRYPOINT may sniff; the seam may not), and the vitest setup files install the driver too. There is deliberately **no default** — an uninstalled driver throws a message naming the fix, because the failure this seam exists to prevent is "the audit log was written with a different SQLite than it was read with", and a convenient fallback is exactly how that would happen unnoticed. Switching drivers while the DB is open throws rather than silently re-opening.

The reason it exists: better-sqlite3 does not merely fail under bun, it takes the process down with an uncatchable N-API panic at construct time (measured with better-sqlite3 13.0.3 under **bun** 1.3.6 and 1.3.14 — those are BUN versions), while `bun:sqlite` is a builtin a `bun build --compile` executable embeds. That is what makes both `claudeui-server` artifacts native-dependency-free for storage. The three engines are held to ONE conformance spec (`src/core/services/__tests__/sqlite-driver-conformance.ts`), run by vitest against `node:sqlite` and real better-sqlite3 where the ABI permits, and by `bun run verify:sqlite` against `bun:sqlite` (vitest cannot host a bun builtin). Two differences are normalised in the seam rather than at ~40 call sites: a `get()` miss is always `undefined`, and better-sqlite3's bare-body `pragma()` is emulated for the two builtins.

**ABI note:** better-sqlite3 13 ships N-API prebuilt binaries (`prebuilds/<platform>-<arch>.node`, `NAPI_VERSION` in its `binding.gyp`) that load under both plain Node and Electron, so the old "bun leaves a Node-ABI build that crashes boot with `ERR_DLOPEN_FAILED`" trap no longer applies (`rebuild:native` is still needed for node-pty). vitest still aliases it to `src/test/stubs/better-sqlite3-stub.ts` (a `node:sqlite` adapter) — which is what `betterSqlite3Driver()` resolves to under test. Never import an engine outside its driver adapter.

## Settings & config

`SettingsDialog/` renders the **ADR-065 page model**, and since phase 7 it is the ONLY settings model in the tree: twelve pages in three rail groups (App / Features / Engines), each page an ordered list of groups, each group a card of rows built from one `SettingRow` vocabulary. `settings-pages.tsx` owns the model (`PAGES`, `RAIL_GROUPS`, the `pageOf` / `visibleGroups` / `itemsFor` / `storageOf` / `noteOf` / `appliesOnOf` lookups, `searchSettings` and the shared `bucketSearchHits` reducer); `settings-sections.tsx` holds the per-item render bodies as `SECTIONS` and nothing else — the store-derived scope model that used to live at its tail (`SCOPES`, `SECTION_SCOPE_MAP`, `firstSectionOfScope`, `isSectionVisible`, the per-scope id sets) is deleted, with no replacement, because storage location is no longer navigation. `SECTION_TARGET` survives as the INVENTORY map only: nothing renders from it, and the model test walks it to prove no pre-arc section lost its home. `settings-target.ts` carries what the model, the shell and the item bodies all need and imports nothing itself: the page ids, `SettingsTarget`, `groupKey` and the `open-settings` detail parser.

The phone (<768px, ADR-048) renders the SAME model — three tabs, one per rail group, pages as lazily mounted accordions, and inside an open page the same group cards the desktop draws. There is no adapter and no second model: the two presentations share `settings-pages.tsx`, the row vocabulary, the bucketing of search results, and the three props the container computes for both (`engineByGroup` / `onSelectEngine` / `navigate`); what differs is markup. A group whose values differ per engine declares `byEngine` item lists and renders an engine segment, a setting that exists for some engines only carries an engine chip, and groups gated on a capability declare `requires: 'sandbox' | 'proxy'` (evaluated against the page's engine). Where a group writes lives on its header as a storage tag; it is information, never navigation. A group's storage tag, note and applies-later badge may each be a function of the selected engine, and a `byEngine` group may declare `engineFrom: '<sibling group id>'` to follow that sibling's engine segment instead of drawing its own (the Dispatch page's Limits card). The dispatch panes share ONE config object per engine through a small reference-counted store, because `config:save-engine-config` replaces the whole file and two independent copies on one page would clobber each other. Deep links are `open-settings` events with a `{ page, group? }` detail, parsed by one helper both dialog hosts call.

- **Neutral autonomy modes** — `AutonomyMode = 'plan' | 'ask' | 'autoEdit' | 'full'`, mapped per engine (Claude permission modes; opencode rulesets per ADR-022), gated on `capabilities.autonomyModes`.
- **Claude-owned config** (Sessions & autonomy + Engines › Claude pages) — permission rules (allow/deny/ask at user/project/local scope), sandbox, proxy, dispatch config.
- **opencode-owned config** (Engines › opencode + Models & providers pages) — native opencode config edited in the UI and written to opencode's own files (models, agents — ADR-028/029/031), plus dispatch config. Providers are no longer a pane of their own on either side: Models & providers › Providers is ONE list over the `provider-registry:list` read model, one row per provider IDENTITY across the shared vault, opencode's catalog + credential rows (opencode 2.x keeps credentials in its DB, ADR-097 §5) and pi's `auth.json` / `models.json`, with a Manage sheet and an Add sheet behind it. The engines' own model editors (`OpencodeProviderConfigModal`, `PiProviderModal`) are reached FROM that sheet.
- **Vendors** — the Anthropic form (endpoint + model override) is editable; writes go to `vendors/anthropic.json` and apply at spawn.
- **Spawn wiring** — `session:create` sources launch params from the engine/vendor stores; the vendor derives from the active model's `ModelRef`. `config:save-settings` strips engine/vendor-owned fields from incoming payloads.
- A read-time, idempotent migration (`ui-config.migrateConfigPlane()`) moved legacy flat-settings fields into the engine/vendor stores.
