# Codex integration follow-ups — kickoff specs

Post-merge follow-ups to the Codex integration (PR #37 merged into `pre-release` on 2026-09-14). Worked on `codex-integration` under ADR-026: the main model writes the kickoff, an implementing agent builds against it, the main model reviews every line, re-runs the gates, drives the real app and commits. Each landed slice gets a "Landed" paragraph recording the as-built deviations.

## Standing rules for implementing agents

- Never run `git add`, `git commit`, `git stash`, `git checkout`, `git reset`, `git clean`, `git branch` or `bun install`. The working tree is shared; report the exact list of files you created or changed, and nothing else may differ in `git status`.
- Never run `bun run format` (it rewrites the repo). Format only the files you touched: `bunx prettier --write <file>…`.
- Never delete or rewrite a file you did not create in this task.
- No real credentials, no real sign-ins, no real provider turns. Tests use fakes, ephemeral ports and scratch homes.
- Every behaviour change ships with a guard test proven to FAIL before the fix: quote the failing assertion in your report.
- Gates before reporting: `bun run typecheck`, `bun run lint`, the test files you touched, then `bun run test` once. Quote the summary lines.
- Answer "what does the code do" from the source, not from memory. Paths under `docs/` named below are the design record.
- Report deviations from this spec explicitly, with the reason.

## F2 — the headless server must not bind port 1455 for a ChatGPT PKCE sign-in

**Facts:** the ChatGPT OAuth client is registered to `http://localhost:1455/auth/callback` (ADR-057), so the redirect URI cannot change. `CodexLoginFlow.start()` (`src/core/auth/vault/codex-oauth.ts`) binds a loopback listener on 1455 before returning the authorize URL. On the headless server the redirect never reaches that listener (it lands on the browser's own loopback and the code arrives by paste-back, `completeFromPastedInput`), so the listener is dead weight and two concurrent server sign-ins collide on the port (spec residual in `docs/codex-accounts-spec.md` Slice 7 Landed paragraph). `AuthVault` (`src/core/auth/vault/AuthVault.ts`) builds flows through `loginFlowFactory`, defaulting to `new CodexLoginFlow({ now })`; the module singleton `authVault` takes no deps. `src/core/host.ts` is the host seam: each hook has a setter, the desktop main sets it, the headless server leaves it unset and the fallback IS the headless behaviour (read the file header).

**Change:**

1. `CodexLoginFlowOptions.loopback?: boolean` (default `true`). With `false`: `start()` skips `listen()`, still generates PKCE/state, still arms the pending promise and the timeout, and the authorize URL's redirect is `http://localhost:${DEFAULT_OAUTH_PORT}/auth/callback` exactly as before. `completeFromPastedInput`, `cancel()`, `terminate()` and `settled` work unchanged; `terminate` must tolerate `server` being undefined (check every `this.server` use).
2. A host hook in `src/core/host.ts` following the file's conventions, e.g. `setHostOAuthLoopback(enabled: boolean | null)` / `hostOAuthLoopback(): boolean`, whose fallback (unset) is `false`, i.e. no loopback on a headless host. The desktop main sets it to `true` where it sets the other host hooks (find the call sites of `setHostPaths` / `setHostAuth` in `src/main` and add it there). The server sets nothing.
3. `AuthVault`'s default `loginFlowFactory` passes `loopback: hostOAuthLoopback()` at CALL time (not at construction, so the desktop's late wiring is honoured).
4. Do not change `PiAuthProvider.oauthAuthorize`'s `instructions` string or the renderer.

**Guard tests (proven failing first):**

- `CodexLoginFlow` with `loopback: false`: two flows `start()` concurrently with the same fixed ephemeral port and neither throws `EADDRINUSE`; after `start()` a probe server can `listen()` on that port (nothing is bound); the authorize URL still carries `localhost:<port>/auth/callback`; `completeFromPastedInput` with a matching state completes through the mocked exchange; `cancel()` rejects the pending wait; the timeout still fires. Model them on `src/main/auth/vault/__tests__/CodexLoginFlow.test.ts`.
- `AuthVault` default factory: with the host hook unset, `beginLogin()` produces a flow with no listener; with the hook set to `true`, it binds (use port 0 through whatever seam the test needs; if the default factory must accept a port for testability, add it to the deps, not to the singleton).
- The desktop wiring: if `src/main` has a test that asserts the host hooks it sets, extend it; if not, say so and the main model verifies by driving the desktop app.

**Docs:** one bullet under the Slice 7 Landed paragraph's residual in `docs/codex-accounts-spec.md` saying it is fixed and how; one line in `docs/architecture/security.md` or `remote.md` ONLY if either describes the loopback today (grep `1455` first; do not add a section).

**Landed 2026-09-14 (`a1c54df2`, on `pre-release`).** As specified. Deviations: `AuthVaultDeps.loginFlowPort` (test-only seam for the default factory, absent from the singleton); the tests probe with a `127.0.0.1`-bound server because the existing wildcard probe coexists with a loopback bind on Windows and could not prove "nothing listens"; the desktop wiring lives in `bootCore()` (`src/main/boot-core.ts`), guarded by a new case in `windowless-boot.e2e.test.ts` since no boot-core unit test existed. Reviewer changes: `src/server/main.ts` now calls `setHostOAuthLoopback(null)` explicitly beside its other host hooks, and the test that probed the real port 1455 for emptiness was trimmed to the redirect-URI assertion (the ephemeral-port case already proves no bind; a dev box mid sign-in would have failed it spuriously). Neither `security.md` nor `remote.md` mentions the loopback, so neither changed. Verified: the three guard files plus the dialog suite (89 tests), typecheck, lint; a desktop drive on an isolated profile showed `127.0.0.1:1455 LISTENING` for the app's PID throughout the PKCE wait and gone after Cancel. The server side rests on the `AuthVault` default-factory tests, which exercise the exact production path (module singleton, no host hooks); no hermetic-server drive was run.

## F4 — Render-loss detector: audit the projection at every turn end

Ruled 2026-09-15: the intermittent render loss stops being "track only". Two of twenty real-turn desktop drives on 2026-09-12 (first turn of a new Codex session, test suites running concurrently) rendered only the user bubble and a spinner while core's canonical held every message. Which renderer layer lost them, the fold or the projection, was never captured. This slice makes the next occurrence self-reporting.

**Facts (verified 2026-09-15).** The store's `messages` is a by-reference projection of the replica canonical: `projectSession` in `src/renderer/src/stores/replica.ts` assigns `messages: c.messages`, committed through `commit` → `buildPatch` with an identity diff. After any commit, `store.sessions[id].messages === getReplicaState().sessions[id].messages` must hold for every id canonical knows; a difference IS a projection bug. Events fold in `startReplica`'s tap; post-fold observers register through `onReplicaApplied(cb)`. `session:status` is a canonical channel (`src/core/shared/sync/channels.ts`) and its `state` reaches `idle` / `error` / `disconnected` at turn end; a Codex rekey (minted routing id → native thread id) rides the same channel (`pendingRekeyFor`), and `resolveRekeyed(id)` follows a retired id. `SyncClient` (`src/core/shared/sync/sync-client.ts`) requests a resync on a seq gap in `ingest` and `drain`, and `applyFullState` REPLACES canonical; nothing counts how often that happened. Renderer-to-main logging exists: `window.api.logRelay(level, source, message)` (preload `src/preload/index.ts`, web `src/web/api-adapter.ts`, sink in `src/main/index.ts` → the main logger at that level). Verifier hooks live in `src/renderer/src/utils/verifier-hooks.ts` (`buildVerifierSnapshot`), installed when `window.api.verifierHooks === true`.

**Build:**

1. New module `src/renderer/src/utils/projection-audit.ts`, started once next to `startReplica()` (find the entry points; desktop and web both). It registers through `onReplicaApplied`, never a second event tap. On every `session:status` event whose new state is `idle` or `error` (read the event args; do not re-derive), schedule ONE audit for that session id after `PROJECTION_AUDIT_DELAY_MS` (1500), coalesced per id and cancelled by a later `running`. The audit reads the store and `getReplicaState()` and computes four findings:
   - `projection`: canonical has the id and `store.sessions[id]?.messages !== canonical.sessions[id].messages`.
   - `retired`: a store session key `k` with `resolveRekeyed(k) !== k` (a retired id still resident, so the rekey's carry-over failed).
   - `emptyTurn`: canonical's messages for the id end on a `user` message after an `idle` (not `error`) status. This is the symptom itself regardless of the layer that lost the reply. Read the message union in `src/shared/types.ts` and exclude what legitimately ends on the user: an interrupted turn, a queued or held prompt marker if one exists. Say in the report exactly what you excluded.
   - `resyncs`: a monotonic `resyncCount` on `SyncClient`, incremented wherever `requestResync` is invoked, with a getter reachable from the renderer beside the registry in `src/core/shared/sync/client-registry.ts`. Report the exact export.
     Any finding → `window.api.logRelay('warn', 'ProjectionAudit', <one line of JSON: id, finding kinds, store and canonical counts by role, retired ids, resyncCount, lastSeq if reachable>)`. No finding → nothing (no per-turn info noise). The audit never throws, never mutates state and never triggers a resync: a cure would hide the evidence.
2. Extend `VerifierSnapshot` with `resyncCount` and, per store session, `endsWithUser: boolean`, so a harness loop can assert without parsing logs.
3. Guard tests, each proven failing first: (a) unit, the audit function over hand-built store/canonical pairs, each finding kind alone and none for the healthy case; (b) through the real replica: fold `session:created` → `session:status` running → a user message → `session:status` idle with no assistant message, advance fake timers 1500 ms, assert one `logRelay` call carrying `emptyTurn`; the same sequence with an assistant message folded → no call; (c) a Codex-style rekey through `session:status` → no `retired` finding, and one when the store is hand-corrupted with the old key; (d) the `SyncClient` counter increments on a gap.
4. Docs: one paragraph in the renderer replica section of `docs/architecture/sync-core.md` naming the audit and its findings; one line in `docs/testing-strategy.md` where the verifier snapshot is described, if it is.

**Report:** files, the gates, the failing assertions quoted, and the exclusions from `emptyTurn`.

**Landed 2026-09-15 (on `pre-release`).** As specified, with these deviations accepted from the implementer: `projection` scans EVERY id canonical knows (the invariant is global) and reports them in `projectionIds`; `resyncs` is a delta against a baseline taken at the turn's `running` status and carried across a rekey, so a resync that predates the turn is never blamed on it; `emptyTurn` excludes a queued prompt, an open approval and an unsealed streaming buffer, and deliberately NOT a user interrupt (canonical carries no interrupt marker; an interrupt before the first token costs one warn line). The getter is `getSyncResyncCount()` in `client-registry.ts`; the audit starts beside `startReplica()` in both entry points, idempotent. Two web component tests gained `onReplicaApplied` in their replica mock (17 unhandled rejections otherwise). One reviewer fix: every `running` status re-took the baseline, and a Codex rekey rides a status that is usually still `running`, so a resync between the first turn's start and its rekey could never be attributed; only the first `running` of a turn now takes the baseline (fresh when a `running` cancels a pending audit). Its guard test failed before the fix (`expected "vi.fn()" to be called 1 times, but got 0 times`) and also fails when the rekey carry-over is mutated away, which nothing had guarded. Verified: typecheck, lint, the four touched files (61 tests, 24 in the audit file), full `bun run test` (673 files, 12505 tests), and live in the real app on an isolated home against the fixture provider: 20 first-turn Codex sessions under 12 load workers logged no `ProjectionAudit` line, and a hand-corrupted store entry (the first session's `messages` replaced by a copy) produced exactly one warn line at the next session's turn end, `findings: ["projection"]` with `projectionIds` naming the corrupted session. Follow-up noted, not fixed: in the replica's tap `persistRekeyedRegistry` runs BEFORE the post-apply observers and reaches disk; if it throws, the sync client's fence swallows it and every observer (sounds, attention marks, the historical load, this audit) is skipped for that event.

## F6 — A throwing rekey persist must not skip the post-apply observers

**Facts (verified 2026-09-15).** In `src/renderer/src/stores/replica.ts`, `startReplica()`'s tap folds a canonical event, updates the in-memory rekey bookkeeping, and then calls `persistRekeyedRegistry(rekey.newId)` for a rekey, which reaches disk through `useSessionStore` (`recordSessionEngine` / `persistSessionRegistry` → `window.api.saveSessionConfig`).
