# Codex integration follow-ups — kickoff specs

Post-merge follow-ups to the Codex integration (PR #37 merged into `pre-release` on 2026-09-14). Worked on `codex-integration` under ADR-026: the main model writes the kickoff, an implementing agent builds against it, the main model reviews every line, re-runs the gates, drives the real app and commits. Each landed slice gets a "Landed" paragraph recording the as-built deviations.

## Standing rules for implementing agents

- Never run `git add`, `git commit`, `git stash`, `git checkout`, `git reset`, `git clean`, `git branch` or `bun install`. The working tree is shared; report the exact list of files you created or changed, and nothing else may differ in `git status`.
- Never run `bun run format` (it rewrites the repo). Format only the files you touched: `bunx prettier --write <file>…`.
- Never delete or rewrite a file you did not create in this task.
- No real credentials, no real sign-ins, no real provider turns. Tests use fakes, ephemeral ports and scratch homes.
- Every behaviour change ships with a guard test proven to FAIL before the fix: quote the failing assertion in your report.
- Gates before reporting: `bun run typecheck`, `bun run lint`, the test files you touched, then `bun run test` once. Quote the summary lines.
- Answer "what does the code do" from the source, not from memory. Paths under `docs/` named below are the design record.
- Report deviations from this spec explicitly, with the reason.

## F1 — `claudeui-server` zips for macOS arm64 and Windows x64

**Ruling (Daniel, 2026-09-14):** Linux keeps its two `tar.gz` legs unchanged. macOS ships one server artifact, arm64 only, as a zip. Windows ships one, x64 only, as a zip. Both release workflows stay mirrored.

**Where:** `.github/workflows/pre-release.yml` and `.github/workflows/release.yml` (mirrored, apart from the release-note wording already differing), `docs/adr/adr-061_ci-build-gates-and-release-artifact-matrix.md` (amend the artifact matrix and add a dated amendment section; do not rewrite the history), `docs/architecture/codex.md` line ~56 (the sentence naming the Linux tarballs). Do not touch `scripts/build-server.mjs` unless a real defect blocks the build; report it if so.

**Build:** in the desktop `build` matrix job, after the existing "Upload artifact" step (the vendored engines are all present by then: postinstall ran `ensure-cli`/`ensure-opencode`/`ensure-pi`/`ensure-codex` on the host, and `bunx vite build --config vite.web.config.ts` already produced the web bundle), add per-platform steps:

1. `bun run build:server:compile` host-native (no `--target`; the doc comment in `build-server.mjs` says Windows cannot cross-target, and we do not need to), then the boot smoke: `./dist/server-bin/claudeui-server --help` on mac, `.\dist\server-bin\claudeui-server.exe --help` on Windows. `verify:sqlite` runs inside `build:server:compile`; keep it.
2. Assemble a stage directory named exactly like the artifact minus the extension: `claudeui-server-<version>-mac-arm64` / `claudeui-server-<version>-win-x64`, containing `dist/server-bin/.` (executable, `out/web`, `README.md`) plus `vendor/claude-cli`, `vendor/opencode-cli`, `vendor/pi-cli`, `vendor/codex-cli`, mirroring the Linux legs' layout (read their "Assemble tarball" step). Include `vendor/claude-cli` on these two hosts: the patched `bun-claude` exists there, which is the whole reason Linux lacks the Claude engine. Before claiming the Claude engine works from the zip, read how the server locates the claude binary (`src/core` locate logic; start from `codex-locate.ts`'s siblings and `resolveAppPath()` in `src/core/host.ts`) and confirm the vendored path resolves from the staged layout. If it does not, do NOT paper over it: leave `vendor/claude-cli` in the zip, say so in the report, and word the release note honestly.
3. Zip: mac `zip -r -y <name>.zip <stage>` from the workspace root (same tool the desktop mac step uses; `-y` keeps symlinks as links). Windows `Compress-Archive -Path <stage> -DestinationPath <name>.zip` from `pwsh` (same tool as the desktop Windows step). Upload with `actions/upload-artifact@v7`, artifact name = file name, like the other legs.
4. Matrix: add `server_name` (or equivalent) to the two matrix entries rather than hard-coding names in steps.

**Release notes** in both workflows: replace the paragraph that says only Linux tarballs exist. State the four server artifacts, which engines each carries (Linux: opencode, pi, Codex; mac/Windows: those plus Claude Code only if step 2 confirmed it), keep the bubblewrap sentence for Linux, and add one sentence for the mac zip: unpack with `unzip` or Finder so the executable bits survive (Python `zipfile` drops them).

**Not in scope:** ARM Windows, x64 mac, code-signing the server binary, changing Linux to zip, `ci.yml`.

**Landed 2026-09-14 (`37149e02`, on `pre-release`).** As specified, with these deviations: the ADR-061 matrix table was left as written (it is headed "as of this ADR") and the amended matrix lives in a dated amendment section; the Linux `server` job's header comment and a paragraph in `codex.md` were reworded so neither still says the Claude engine is desktop-only; the Windows build step checks `$LASTEXITCODE` after each command because `pwsh` does not abort on a native non-zero exit; the Windows stage uses `Copy-Item -Recurse` onto a not-yet-existing path. ## F2 — the headless server must not bind port 1455 for a ChatGPT PKCE sign-in

**Facts:** the ChatGPT OAuth client is registered to `http://localhost:1455/auth/callback` (ADR-057), so the redirect URI cannot change. `CodexLoginFlow.start()` (`src/core/auth/vault/codex-oauth.ts`) binds a loopback listener on 1455 before returning the authorize URL. On the headless server the redirect never reaches that listener (it lands on the browser's own loopback and the code arrives by paste-back, `completeFromPastedInput`), so the listener is dead weight and two concurrent server sign-ins collide on the port (spec residual in `docs/codex-accounts-spec.md` Slice 7 Landed paragraph). `AuthVault` (`src/core/auth/vault/AuthVault.ts`) builds flows through `loginFlowFactory`, defaulting to `new CodexLoginFlow({ now })`; the module singleton `authVault` takes no deps. `src/core/host.ts` is the host seam: each hook has a setter, the desktop main sets it, the headless server leaves it unset and the fallback IS the headless behaviour (read the file header).

**Change:**

1. `CodexLoginFlowOptions.loopback?: boolean` (default `true`). With `false`: `start()` skips `listen()`, still generates PKCE/state, still arms the pending promise and the timeout, and the authorize URL's redirect is `http://localhost:${DEFAULT_OAUTH_PORT}/auth/callback` exactly as before. `completeFromPastedInput`, `cancel()`, `terminate()` and `settled` work unchanged; `terminate` must tolerate `server` being undefined (check every `this.server` use).
2. A host hook in `src/core/host.ts` following the file's conventions, e.g. `setHostOAuthLoopback(enabled: boolean | null)` / `hostOAuthLoopback(): boolean`, whose fallback (unset) is `false`, i.e. no loopback on a headless host. The desktop main sets it to `true` where it sets the other host hooks (find the call sites of `setHostPaths` / `setHostAuth` in `src/main` and add it there). The server sets nothing.
3. `AuthVault`'s default `loginFlowFactory` passes `loopback: hostOAuthLoopback()` at CALL time (not at construction, so the desktop's late wiring is honoured).
4. Do not change `PiAuthProvider.oauthAuthorize`'s `instructions` string or the renderer.

**Guard tests (proven failing first):**

- `CodexLoginFlow` with `loopback: false`: two flows `start()` concurrently with the same fixed ephemeral port and neither throws `EADDRINUSE`; after `start()` a probe server can `listen()` on that port (nothing is bound); the authorize URL still carries `localhost:<port>/auth/callback`; `completeFromPastedInput` with a matching state completes through the mocked exchange; `cancel()` rejects the pending wait; the timeout still fires. Model them on `src/main/auth/vault/__tests__/CodexLoginFlow.test.ts`.
- `AuthVault` default factory: with the host hook unset, `beginLogin()` produces a flow with no listener; with the hook set to `true`, it binds (use port 0 through whatever seam the test needs; if the default factory must accept a port for testability, add it to the deps, not to the singleton).
- The desktop wiring: if `src/main` has a test that asserts the host hooks it sets, extend it; if not, say so and the main model verifies by driving the desktop app.

**Docs:** one bullet under the Slice 7 Landed paragraph's residual in `docs/codex-accounts-spec.md` saying it is fixed and how; one line in `docs/architecture/security.md` or `remote.md` ONLY if either describes the loopback today (grep `1455` first; do not add a section).

**Landed 2026-09-14 (`a1c54df2`, on `pre-release`).** As specified. Deviations: `AuthVaultDeps.loginFlowPort` (test-only seam for the default factory, absent from the singleton); the tests probe with a `127.0.0.1`-bound server because the existing wildcard probe coexists with a loopback bind on Windows and could not prove "nothing listens"; the desktop wiring lives in `bootCore()` (`src/main/boot-core.ts`), guarded by a new case in `windowless-boot.e2e.test.ts` since no boot-core unit test existed. Reviewer changes: `src/server/main.ts` now calls `setHostOAuthLoopback(null)` explicitly beside its other host hooks, and the test that probed the real port 1455 for emptiness was trimmed to the redirect-URI assertion (the ephemeral-port case already proves no bind; a dev box mid sign-in would have failed it spuriously). Neither `security.md` nor `remote.md` mentions the loopback, so neither changed. Verified: the three guard files plus the dialog suite (89 tests), typecheck, lint; a desktop drive on an isolated profile showed `127.0.0.1:1455 LISTENING` for the app's PID throughout the PKCE wait and gone after Cancel. The server side rests on the `AuthVault` default-factory tests, which exercise the exact production path (module singleton, no host hooks); no hermetic-server drive was run.

## F3 — SignInDialog after Cancel with no stored account

**Facts:** `src/renderer/src/components/auth/SignInDialog.tsx`. On open, `readAccounts()` returns rows; when the list is empty (or mode is `add`) the dialog skips the chooser and calls `start()`. `cancelFlow` cancels the host flow and returns to `choose` only when `accounts.length > 0`; otherwise the stage stays `flow` and the panel keeps its pre-code look ("Requesting a code…" on the device panel, an empty paste panel on the PKCE one) although nothing is running. For Anthropic, `readAccounts` also returns `[]` when multi-account is OFF even though one account exists, so "no rows" has two meanings.

**Ruling (Daniel, 2026-09-14, mockup option B):** Cancel always returns to the chooser, and the chooser handles the empty list.

**Change:**

1. `readAccounts` returns `{ rows, autoStart }`: `autoStart` is true when `rows.length === 0` (no account) or when the provider has one account with multi-account off (Anthropic `!state.enabled`; in that case return the ONE account as a row so the chooser is accurate: label its email, `active: true`). The open effect uses `autoStart || request.mode === 'add'` to skip the chooser, exactly as today for every existing case.
2. `cancelFlow` always `setStage('choose')`.
3. The chooser with zero rows renders, inside the existing `SheetGroup`, one `SettingRow` (`testid` `${DIALOG}.empty`) with the text "No <Anthropic|ChatGPT> account is signed in on this host." followed by the existing add row, whose button reads **Sign in** when the list is empty and **Add another account** otherwise, and whose description reads "Signs in to a <provider> account and adds it to the list." when empty (existing wording otherwise). The button keeps calling `start('add')` for the empty case on ChatGPT; for Anthropic with zero accounts it must call the same thing the open-time skip called (`start('reauth')` today, because `add` goes through `window.api.addAccount()` and `reauth` through `signIn()`; keep that mapping by reusing one helper rather than duplicating the condition).
4. No new stage. No change to `DeviceCodeFlow`, `OAuthPasteBackFlow`, the store, or IPC.

**Guard tests** in `src/renderer/src/components/auth/__tests__/SignInDialog.component.test.tsx` (model on the existing ChatGPT device-code cases; proven failing first):

- Web, ChatGPT, zero accounts: the device panel shows; click its Cancel; `cancelVendorOAuth` was called; the dialog now shows `${DIALOG}.empty` and an add button labelled "Sign in"; the "Requesting a code…" text is gone.
- Clicking that "Sign in" starts the device flow again (`authorizeVendorDeviceCode` called a second time) and the panel returns.
- Anthropic with multi-account off: the dialog auto-starts as before; Cancel shows the single account row with Re-authorize, not the empty state.
- The existing "add mode skips the chooser" and "lists the vault accounts" cases still pass unchanged.

**Docs:** one sentence under the Slice 7 Landed paragraph's residual in `docs/codex-accounts-spec.md` (a different sentence from F2's; both edit the same paragraph, so the F3 implementer appends its sentence at the END of that paragraph and F2's at the position of the residual text — the main model resolves overlap at review).

**Landed 2026-09-14 (`73282fe9`, on `pre-release`).** As specified, with these deviations: `cancelFlow` also clears `busy`, because the cancelled `start()` stays parked in the device-code poll for up to one cadence and would have left every chooser button disabled; the empty chooser's button calls the same `startWithoutChoosing()` helper the open-time skip uses; the empty-state row renders only once the account read has settled (`accounts !== null`), so the dialog never claims "no account" before the list arrives. Reviewer additions after the implementer flagged two gaps: `readAccounts` also returns `canAdd`, false for Anthropic with multi-account off, which hides the add row there (`AccountManager.addAccount()` would silently enable multi-account, a Settings decision) and, when that host lists no account at all, offers Sign in without the "no account is signed in" row (the keychain credential is invisible to this list). Four guard tests, three proven failing pre-fix (`expected <div …> to be null` on the surviving device panel; `Unable to find … SignInDialog.addAccount`; `Unable to find … SignInDialog.account`) plus one for the reviewer case. Verified: the dialog suite (23 tests), typecheck, lint, full `bun run test` (670 files green after the `codex-locate` posix fix in `bfce2c7c`), and a desktop drive on an isolated profile with no vault account: open → waiting panel, Cancel → the empty-state row and a "Sign in" button, no "Requesting a code…" (screenshot `f3-after-cancel.png` matches mockup option B). Note for the owner: each desktop drive opens a real browser tab on the authorize URL (`window.open` in the store); nothing was signed in, and the tabs can be closed.
