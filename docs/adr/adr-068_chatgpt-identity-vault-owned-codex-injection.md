# ADR-068: One ChatGPT identity, vault-owned — Codex by token injection, accounts, one sign-in dialog

**Status:** Implemented (2026-09-14, Slices 1–7) on `codex-integration` — see § As built; accepted 2026-09-13
**Supersedes:** [ADR-066](adr-066_codex-fourth-engine.md) §"Authentication is native-owned" and the auth rows of its spec. The rest of ADR-066 and all of [ADR-067](adr-067_codex-shared-permission-model.md) stand.
**Amends:** [ADR-036](adr-036_unified-auth-vault.md) (the vault gains N accounts per provider and a third consumer that is fed by injection, not by file), [ADR-037](adr-037_shared-provider-routing-and-plaintext-vault.md) (`ConfigurableHarnessId` gains `codex`; Codex is a route of the shared `chatgpt` provider), [ADR-065](adr-065_settings-ia-v2-pages-groups-row-vocabulary.md) (the ChatGPT provider row gains a Codex chip and an Accounts card; the Codex engine page is curated like opencode's and pi's; the Codex segment joins Default models, Cross-engine dispatch and the Auto-mode judge), [ADR-014](adr-014_native-anthropic-oauth.md) / [ADR-057](adr-057_remote-vendor-oauth-paste-back.md) (the Claude sign-in UI moves out of the banner and the transcript into one shared dialog; the flow drivers are unchanged).
**Amended by:** [ADR-070](adr-070_one-auth-surface.md) — §3's one dialog held, but §4's "one event, one card" did not: every engine emitted the event AND a companion `session:error`, which is why one credential failure produced four simultaneous prompts. ADR-070 moves the verbatim text onto the event, adds `provider:auth-resolved` so a sign-in clears what it fixed, and replaces the banner/row/composer-hint with one top-bar pill.
**Relates to:** ADR-015 (Claude multi-account, the model this mirrors), ADR-021 (`EngineAuthProvider`), ADR-030 (capability honesty), ADR-045 (opencode disconnect), ADR-047 (opencode server recycle on auth change), ADR-059 (no silent model fallback — the same rule applied to a removed account)

## Context

ADR-066 chose "Codex owns login, credential storage and refresh" for phase 1 and put a single raw pane on Settings › Codex: device-code login, no logout, no accounts, and a description that says no shared-vault credentials are copied. The owner's goal on 2026-09-13 was the opposite: manage the Codex subscription in the app like Claude accounts, hold several ChatGPT subscriptions, reuse the credential across pi, opencode and Codex, and give Codex a real settings page. The two questions were whether the wire allows it, and where every setting belongs.

Reading the Codex source at the pinned tag (`rust-v0.154.0`, sparse checkout under `.cache/codex-src/`, not vendored) answered the first question. Facts the design rests on, with their sources:

- `account/login/start` has a `chatgptAuthTokens` variant `{accessToken, chatgptAccountId, chatgptPlanType?}` (`app-server-protocol/src/protocol/v2/account.rs`). It is gated `#[experimental("account/login/start.chatgptAuthTokens")]`; ClaudeUI already sends `experimentalApi: true` on every `initialize`.
- Tokens supplied this way are held in memory only: `AuthDotJson::storage_mode` forces `Ephemeral` for that mode (`login/src/auth/manager.rs`). Nothing is written to `$CODEX_HOME/auth.json`.
- Codex never refreshes them. On a 401 the app-server sends the client a server request `account/chatgptAuthTokens/refresh` with `{reason: 'unauthorized', previousAccountId}` and waits 10 s for `{accessToken, chatgptAccountId, chatgptPlanType?}` (`app-server/src/external_auth.rs`). The doc comment on `previousAccountId` says it is a hint for "clients that manage multiple accounts/workspaces".
- While external auth is active, native ChatGPT, API-key and Bedrock logins are refused with "External auth is active. Use account/login/start (chatgptAuthTokens) to update it or account/logout to clear it" (`account_processor.rs`). So a live process can be re-pointed at another account between turns, and `account/logout` clears it.
- `account/read` reports an external-token account as an ordinary `chatgpt` account with email and plan parsed from the JWT; `account/rateLimits/read` and the `account/rateLimits/updated` notification work because the auth mode "uses the Codex backend".
- Codex's native ChatGPT mode uses the same OAuth client id and token endpoint as ClaudeUI's vault (`CLIENT_ID = app_EMoamEEZ73f0CkXaXp7hrann`, `https://auth.openai.com/oauth/token`) and refreshes 5 min before JWT expiry or after 8 days; the vault refreshes 15 min early.
- The enum variant carries "[UNSTABLE] FOR OPENAI INTERNAL USE ONLY" — it is the path the Codex desktop app and IDE extension use.

The second question is answered by ADR-065's rules: one home per setting, engine SEGMENT where values differ per engine, engine page for the engine's own file, curated like opencode's and pi's.

## Decision

### 1. The vault owns the ChatGPT identity; Codex is fed by injection only

`chatgpt` becomes a three-route shared provider: `ConfigurableHarnessId` gains `codex`. pi and opencode keep their file feeds. The Codex route is **injection**: after every `initialize` on every app-server ClaudeUI starts (root sessions, the read-only `CodexService` client, headless dispatch targets) the host sends `account/login/start {type: 'chatgptAuthTokens'}` from the vault's current access token, and answers `account/chatgptAuthTokens/refresh` from the vault. The vault's `CredentialSync` remains the single refresh owner. No file under `~/.codex` is written for auth, the refresh token never reaches Codex, and the rotating-refresh-token hazard ADR-036 has to manage for pi and opencode does not exist for Codex.

The refresh handler answers from the vault's cached access token first and only falls through to a network refresh when the cached token is itself expired; the 10 s deadline is otherwise easy to miss. A vault refresh that fails with `invalid_grant` makes the handler answer an error, the turn fails, and the session raises the auth-required event of §4.

Owner rulings recorded here: **inject only** — no `auth.json` vend route for the terminal `codex` CLI; the refresh model may be revisited later. The native device-code flow is **removed** from the product UI (it stays in `CodexService` as tested code). The "[UNSTABLE]" label is accepted: the binary is pinned, `check-codex-protocol` regenerates the types on every bump, so a removal fails loudly at bump time, never silently in the field. When Codex refuses an injected token (a workspace pin — on 0.154.0 a user-level `forced_chatgpt_workspace_id` did not gate the login in the real-binary test, so in practice this means a managed `allowed_chatgpt_workspaces` policy) the native refusal is surfaced verbatim and the session does not start under another identity.

### 2. Accounts: a global active account, per-session pinning behind a toggle

The vault schema goes from one credential per provider to a list of **accounts** per provider (`{id, email, accountId (workspace), planType, credential}`) plus an **active** account id. `CredentialSync` refreshes every stored account on its own timer. pi and opencode, whose stores are single-slot, receive the active account only; switching it re-vends both and recycles opencode per ADR-047. Switching the active account affects **new** Codex sessions only — a running session keeps the token it started with, because a live switch would change usage attribution mid-conversation.

A per-provider toggle **Per-session accounts** (off by default, hidden with one account) enables pinning. When on, a Codex session's input bar shows an account picker offering "Follow active account" or any stored account. The pin is stored with the session's overrides beside model and effort, applies from the next turn by re-injecting the live process, is inherited by forks, and is re-injected on resume; headless dispatch targets run under the caller's pin. A pinned account that no longer exists makes the session fall back to the active account with a visible notice, never silently (the ADR-059 rule applied to accounts). The picker is gated by a new `capabilities.auth.perSessionAccount`, true for Codex only. Claude could adopt the same pin later through a per-spawn credential directory; that would change today's respawn-all switch and is a separate decision.

Usage: per-account `account/rateLimits/read` through the service client, plus `account/rateLimits/updated` from live sessions, rendered in the sidebar usage panel next to Claude's. The Codex `RateLimitWindow` (`usedPercent`, `resetsAt`) maps onto ClaudeUI's `RateWindow` one to one.

### 3. One sign-in dialog for every provider and every entry point

A single `SignInDialog` replaces the flow UI that today lives in four places: the Claude top banner (which expands into the paste flow on web), the inline `AuthErrorBlock` in the transcript, the opencode `VendorAuthRequiredCard`, and the settings account rows. The dialog has a provider header, an account chooser (re-authorize the expired one, switch to another stored one, add a new one) and a flow panel whose **driver** is per provider — vault PKCE for ChatGPT (loopback capture on the desktop, ADR-057 paste-back remotely), cli.js control requests for Anthropic (ADR-014, `manualUrl` paste-back remotely) — and whose **host variant** is derived from the connection, never chosen by the user. It is dismissible while waiting; the flow continues and the banner reflects it. Its done state reports the fan-out: which Codex sessions were re-injected, which engine stores were rewritten, that opencode picks the change up on its next server start, and a "Retry last prompt" when a prompt failed.

Entry points stop carrying flow UI. The top banner becomes one line whose only action opens the dialog. The transcript gets a compact "turn stopped, credential rejected" row with a Sign in link. Settings rows, greyed model-picker entries, the welcome tile and the session account picker open the same dialog in the matching mode. The owner acknowledged this touches Claude's existing surfaces.

Device code is **not** a general fallback. It is reserved for the headless server, where no host browser exists, and if built it is ported from Codex's own `deviceauth/usercode` and `deviceauth/token` flow against the same issuer into the vault, not run through a throwaway native login.

### 4. One auth-required event from every engine

Every engine emits the same `session:auth-required {providerId, accountId?}` when a credential is rejected: opencode already does (`session:vendor-auth-required` is renamed and generalized), Codex raises it when the refresh server request cannot be answered, pi when its provider returns an authentication error, and Claude keeps cli.js's own `auth-source` signal feeding the same banner. One event, one card, one action against the vault.

### 5. Codex inherits the shared MCP list

The app already treats Claude's MCP configuration (`.mcp.json` and `settings.json` across user, project and local scopes, with the per-directory disabled list) as canonical, and translates it into opencode's runtime config at spawn without touching opencode's files. Codex gets the same: a translation into Codex's `mcp_servers` shape (stdio → command/args/env; remote → url, bearer-token env var, static and env-sourced headers) delivered as the `config` override on `thread/start` and `thread/resume`. Native entries the user declared in `config.toml` (including OAuth-authenticated servers, which Claude's shape cannot express) stay untouched and work alongside. **Gate:** the runtime override path must be proven on the real binary with the mock-model fixture before this is wired; `model_catalog_json` is documented as a per-thread no-op, so `mcp_servers` must be checked, not assumed. The fallback of writing into the user's `config.toml` under a ClaudeUI prefix is materially worse and is taken only if the probe fails.

### 6. Settings: where every Codex key lives

Writes to Codex's own file go through `config/batchWrite` (present in 0.154.0) with `expected_version` for optimistic concurrency and `reload_user_config` where the key is hot-reloadable; ClaudeUI never parses or rewrites TOML itself. `thread/start.config` is available for session-scoped values. The typed method map gains `config/value/write`, `config/batchWrite`, `account/rateLimits/read` and the two notifications.

## Consequences

- ADR-066's "native-owned auth" section and the spec's auth rows are superseded; `CodexAuthProvider`'s device-code flow, the `codex:login-*` channels and `CodexAccount.tsx` are removed once the injection path is verified live.
- The vault file moves to a v3 schema (accounts list + active id) with a read-time migration from v2's single credential; `CredentialSync` refreshes N accounts and vends the active one to pi/opencode. `provider-registry:list` gains the account list and the active id for the ChatGPT row.
- `SessionStatus.account` for Codex carries the vault account id; `codex_session_overrides` gains an `accountId` key in its JSON blob (no schema migration). Usage rows attribute to it.
- The Claude banner, `AuthErrorBlock`, `VendorAuthRequiredCard` and the settings paste-back rows collapse into `SignInDialog` plus one banner line and one transcript row. `OAuthPasteBackFlow` survives as the dialog's remote panel.
- Codex threads start with an inherited MCP list once the override probe passes.
- Trust posture is unchanged from ADR-036: ClaudeUI is already a third application on the shared OpenAI client id; Codex receiving tokens from the vault is the same client id it would use itself.
- No commit or push is authorized by this ADR; ADR-026's loop applies to every slice.

## Phases (each one reviewed slice, one or more commits)

1. **Vault accounts** — v3 schema and migration, per-account refresh, active-account vend, `provider-registry` projection, `provider-account:*` commands (list, add via the existing PKCE flow, switch, remove, set per-session toggle), the Accounts card and route toggles in the ChatGPT Manage sheet.
2. **Codex injection** — `codex` route; inject after `initialize` in `CodexSession`, `CodexService` and the dispatch target; `account/chatgptAuthTokens/refresh` handler; `AccountRef` and `accountId` override; per-session picker behind the toggle and capability; rate limits into the usage panel; remove the device-code UI and channels.
3. **Sign-in dialog** — `SignInDialog`, `session:auth-required` from all engines, banner and transcript row, entry points rewired, Claude paste-back moved into the dialog.
4. **MCP inheritance** — the override probe, then the Codex translation on `thread/start` / `thread/resume`.
5. **Settings** — typed config methods, the Codex engine page groups, Codex segments on Default models, Dispatch and the judge, stale-copy fixes.

## As built (2026-09-14)

All five phases landed on `codex-integration` as eight reviewed slices (`855755af` Slice 1, `786902fd` 2a, `81822982` 2b, `a54776e7` 3, `772d89eb` fix, `37ccd411` 4, `c3c32850` 4b, `3be8e0b2` 5a, and the 5b commit after it). Every as-built deviation is recorded per slice in the accounts spec, deleted once the arc landed (`git log -p -- docs/codex-accounts-spec.md`); the ones that change what this ADR says:

- **§1** holds: injection is memory-only, the host answers `account/chatgptAuthTokens/refresh` from the vault, and a user-level `forced_chatgpt_workspace_id` does not gate an injected token. A migrated v2 account's id is derived, not random.
- **§2**: `removeAccount` rings the active-changed hook on every path that changes what the engines hold, so opencode is recycled per ADR-047.
- **§4**: pi initially emitted no `session:auth-required` (it had no distinguishable auth error). **No longer true as of `0a8d80a9` (2026-09-19)**, which added a 401/403 classifier to pi's event mapper — 429 and 5xx deliberately excluded, since a quota the same credential will serve again is not a sign-in problem. All four engines now raise the event. The "one card" half of §4 was not achieved at all until [ADR-070](adr-070_one-auth-surface.md) — see its Context.
- **§5**: the per-thread `config.mcp_servers` override MERGES per key into the native table (probed), so the `config.toml`-writing fallback was never needed. MCP tool approvals arrive as `mcpServer/elicitation/request` (no question id; accept body `{ action: 'accept', content: {} }`) and plan mode DECLINES kind `mcp`, as the shared ladder does for every engine.
- **§5, amended 2026-09-16 (F17):** the per-thread `config` override is no longer only the inherited Claude servers. It now ALWAYS carries `features` (the nine desktop-app flags off) and, on a machine where the Codex desktop app shares `~/.codex`, `mcp_servers.<name>.enabled = false` for its own servers (`node_repl`, `cua_repl`, `computer-use`, or any command inside a `.app/Contents/` bundle) and `plugins.<id>.enabled = false` for its `@openai-bundled` plugins — the desktop app writes all of those into the USER's `config.toml` and nothing in the binary gates their loading on which client opened the thread. The set is DETECTED from the effective config (`codex-desktop-entries.ts`), never assumed: an `enabled: false` overlay on a server the user does not have creates a table with no transport and fails config load. "Absent, not empty" still holds per key — a user with neither an inherited server nor a desktop one sends no `mcp_servers` and no `plugins` key at all — and a name in both tables keeps its transport and gains the flag rather than being replaced. Still not a write: `docs/architecture/codex.md` § Tools and dispatch has the detail.
- **§6**: `config/batchWrite` semantics on 0.154.0 — `value: null` removes a key (so Reset is a removal and "modified" means present in the base user layer); a stale `expectedVersion` fails with the camelCase tag `configVersionConflict` in `error.data.config_write_error_code`; keys are NOT validated against the schema, so the page's key list was taken from `config_toml.rs`. `browser_use.enabled` / `computer_use.enabled` do not exist; the gates are `features.browser_use` / `features.computer_use`. `service_tier` offers `priority`/`flex`; `personality` is an enum (no custom text). Raw config is read-only (`batchWrite` has no whole-file form). Two toggle defaults were corrected against the source: `shell_environment_policy.ignore_default_excludes` defaults to `true`, and analytics are off under `codex app-server` unless `--analytics-default-enabled` is passed (ClaudeUI does not). IPC results that cross `window.api` must not carry an `ok` key (the transport envelope); the config write result is discriminated on `status`.
- **§6, topic pages**: `engines/codex.json#codexConfig { defaultModel, defaultEffort }`; a configured default is explicit (ADR-059); the effort is paired with the configured model and never sent on a resume; an empty Codex catalog keeps its own sign-in diagnosis rather than naming the configured model. `DISPATCH_CALLERS` was corrected for all four engines (Codex both hosts and accepts `dispatch_agent`). The compiled-rules chip on the Permissions row appears only when the Codex binary is installed.
- **§3, entry points (Slice 6, same day):** the model picker lists a "Sign in to Claude/ChatGPT" item above a dimmed group whose provider is unauthenticated, and a session that has not spawned shows one composer row with a Sign in link — the mockup's engine tile, relocated because the app has no engine tiles. The renderer's one auth view (`providerAuth`) derives Anthropic from the engine probe and ChatGPT from `provider-registry:list`; `'unknown'` never renders as signed out.
- **§3, device code (Slice 7, same day):** built for remote clients as the web client's default ChatGPT sign-in — a port of Codex's `deviceauth` flow into the vault, host-owned wait, one start command and one polled status query, three display fields on the wire, paste-back one tap away; the headless server now serves the pi (vault) and Codex auth providers and refuses only Claude and opencode.
- Deferred from this arc: pi raises no `session:auth-required`; Codex→Codex dispatch stays refused; the macOS legs of the new integration tests have not run.
- **§2, what a switch does (as built after ADR-069 §4, restated 2026-09-16):** "a running session keeps the token it started with" holds only for a session PINNED to an account; a session that follows the active account is disconnected by the switch (it leaves its host) and resumes under the new account on its next message, which is also what a Claude switch does (`invalidateLiveSessions` cancels every live Claude session; ADR-015's "respawn" is that cancel plus the next send's resume). The Accounts page states both rules in those words.
- **§2, where accounts are managed (F14, 2026-09-16):** every provider's stored accounts live on **Models & providers › Accounts**, as one group per provider in rail order (Anthropic, then ChatGPT) — the ChatGPT rows moved out of the Manage sheet, which now carries one link row naming the count; "Disconnect all accounts" stays in the sheet's footer, being a provider action. Switch semantics are **unchanged and stated per group**, because they differ: Claude respawns every running session on the new account (ADR-015), a running Codex session keeps the account it started with while pi and opencode follow the active one (§2 above). Unifying them is a separate decision. The ChatGPT provider row now chips **Codex**, enabled exactly when the vault has an ACTIVE account: Codex is injection and never a route (§1), so nothing else on the row would have said the subscription reaches it, and the sheet's ENABLED FOR carries a read-only Codex row saying the same. On every ChatGPT/Codex surface a workspace is now named "ChatGPT workspace" with one explainer line where the accounts appear — a bare "Workspace" reads as a directory everywhere else in the app.

## Alternatives considered

- **Keep native-owned auth and adopt tokens into the vault afterwards** (ADR-066's deferred direction). Rejected: two refresh owners for one rotating refresh token, the exact hazard ADR-036 exists to remove, and no path to per-session accounts.
- **Per-account `CODEX_HOME`** (mirroring ADR-015's per-account credential directory). Rejected: fragments Codex's history, rules, config and MCP OAuth stores per account, and still leaves Codex refreshing on its own.
- **Also vend to `~/.codex/auth.json`** so the terminal CLI shares the login. Deferred by owner ruling; it reintroduces a second refresher.
- **Device code as the general fallback.** Rejected: the dead-page paste-back already works remotely; device code is kept for the headless server only.
- **Native MCP list editor on the Codex page.** Rejected: MCP is already shared canonically from Claude's config; Codex joins that, as opencode did.
