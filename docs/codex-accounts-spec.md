Realizes [ADR-068](adr/adr-068_chatgpt-identity-vault-owned-codex-injection.md). Five reviewed slices under [ADR-026](adr/adr-026_development-workflow.md): the main model writes the kickoff, an Opus implementing agent builds it, the main model reads every changed line, re-runs gates, drives the real app and commits. Mockups reviewed by the owner on 2026-09-13 are the visual target (five screens: providers and accounts, Engines › Codex, Codex on topic pages, per-session account picker, sign-in dialog).

Standing rules for every implementing agent on this spec:

- No `git add`, `commit`, `stash`, `checkout`, `reset`, `branch`, `push`. No `bun install`/`add`/`remove`. No `bun run format` over the repo (format only the files you created or changed, by path). Do not delete or revert any file you did not create. Report the exact file list you touched; the reviewer diffs it against `git status`.
- No real credentials. Never read `~/.claude/ui/auth-vault.json`, `~/.codex/*`, `~/.pi/agent/auth.json` or opencode's `auth.json`. - Report results and deviations; never self-certify.

## Slice 1: vault accounts

**Landed 2026-09-13** on `codex-integration` (the commit after `e23d5f93`). Built as specified; the points where the build refined the design:

- A migrated v2 account's id is DERIVED (`sha256(providerId|workspaceId-or-email)` prefix), not random: the migration runs on every read until the next write, so two reads must agree on the id.
- A credential with no workspace claim matches the active account only when that account has none either (the single slot a v2 migration leaves); it never overwrites an identified account.
- `saveCredential` routes every OAuth record to `upsertAccount` (the vault has no provider-kind lookup; in v3 `credentials` holds API keys only, so the rules coincide).
- `removeAccount` rings `onActiveAccountChanged` on both paths that change what the engines hold (promotion, and last-account removal), not only `switchActiveAccount`; a review found the spec's wording left opencode holding a removed credential (ADR-047).
- The Add sheet keeps its ChatGPT sign-in control once accounts exist, relabelled "Add another account"; the original gate hid it on `connected`, which made "+ Add account" a dead end. Found in review, fixed before commit.
- The Manage sheet renders from `entry.accounts` on the registry row (present but empty on a disconnected ChatGPT row); `provider-account:list` exists for Slice 2's session picker.
- Real-app evidence (isolated temp profile via an `os.homedir()` shim passed with Electron's `-r`, never the owner's home): two fabricated accounts render with the active radio, switch re-vends and moves `activeId`, the per-session toggle persists to `providers/chatgpt.json`, removing the active account promotes the other and hides the toggle; a v2 profile shows its one migrated account and the file stays `v: 2` until the first write.

### Goal

The vault holds N ChatGPT accounts with one active account. `CredentialSync` refreshes every account and vends the active one to pi and opencode exactly as today. The provider registry projects the accounts onto the ChatGPT row, and the Manage sheet shows an Accounts card (radio for active, Remove, Add) and a Per-session accounts toggle. No Codex behaviour changes in this slice.

### Design (decided; do not reopen)

**Vault file v3.** `{ v: 3, credentials: Record<providerId, {type:'api_key', key}>, accounts: Record<providerId, { activeId: string | null, list: VaultAccount[] }> }`. `credentials` keeps only API-key records for custom providers; OAuth subscriptions live in `accounts`. `VaultAccount = { id: string (random, stable), email?: string, accountId?: string (ChatGPT workspace id from the JWT), planType?: string, credential: VaultCredential, addedAt: number }`. Read-time migration: a v2 file with a `chatgpt` OAuth credential becomes one account (id minted, `email`/`accountId` copied) that is active; a v1 plaintext file goes through the existing v1→v2 path first. Malformed entries are dropped as today. Write is the same atomic 0600 rename.

`VaultCredential` gains optional `planType`, parsed at exchange and refresh from the id_token claim `https://api.openai.com/auth`.`chatgpt_plan_type` (same claim sources and order `parseJwtClaims` / `accountIdFromClaims` already use for the account id). Do not change the OAuth constants.

**AuthVault API.** Keep `load()`/`save()` as the ACTIVE account's credential (compatibility for `CredentialSync` feed targets and `getStatus`). Add `listAccounts(providerId)`, `getActiveAccountId(providerId)`, `setActiveAccount(providerId, id)`, `upsertAccount(providerId, credential)` (match by `accountId`: same workspace updates the stored account in place and keeps its id; a new workspace appends; the first account ever becomes active; a re-login of the active account keeps it active), `removeAccount(providerId, id)` (removing the active account promotes the most recently added remaining one, or leaves `activeId` null), `saveAccountCredential(providerId, id, credential)` for the refresher. Existing `loadCredential`/`saveCredential`/`removeCredential` keep working for API-key providers; `saveCredential` with an OAuth record under a subscription provider must route to `upsertAccount` so no caller can silently write the old single-slot shape.

**CredentialSync.** Refresh is per account: one timer per stored account (15 min before its expiry, the existing retry/give-up chain per account, `needsReauth` becomes per account id). `feedAll` writes the ACTIVE account only; `completeLogin` upserts, and feeds only when the upserted account is the active one. Add `switchActiveAccount(id)`: set active, feed both engine stores from the new active credential, then call the injected `onActiveAccountChanged()` hook (Slice 2 wires it; Slice 1 leaves the default a no-op) so the boot seam can recycle opencode per ADR-047 (`opencodeServerManager.recycleAll()` is what `OpencodeAuthProvider` already calls after every auth-store mutation; the hook lets the boot seam do the same without `CredentialSync` importing opencode). `removeAccount(id)`: stop its timer, remove it; if it was active, feed the promoted account or, if none remains, remove both engine copies (the existing `disconnectChatgpt` cleanup). The reconcile-on-start and fs-watch adoption logic keeps operating on the ACTIVE account only: an engine-rotated token is adopted into the active account when it strictly beats it, never into another account. `getStatus()` gains `accounts: Array<{id, email?, accountId?, planType?, expiresAt, needsReauth}>`, `activeId`, and keeps its existing fields for the active account; still never returns token material.

**Shared provider definition.** `SharedProviderDefinition` gains optional `accounts?: { perSession: boolean }` (default false), persisted in `~/.claude/ui/providers/chatgpt.json` by the repository's `normalizeChatgpt` path. Only meaningful for `kind: 'subscription'`.

**Commands** (in `auth-commands.ts`, capability `config`, registered for both transports; add them to the pinned remote channel set): `provider-account:list` → `{ activeId, perSession, accounts: [...] }` from `credentialSync.getStatus()` plus the definition; `provider-account:switch (providerId, id)`; `provider-account:remove (providerId, id)`; `provider-account:set-per-session (providerId, enabled)`. Adding an account reuses the EXISTING sign-in path untouched (`vendor-auth:oauth-authorize` / `oauth-callback` on engine `pi`, vendor `openai-codex`, which delegates to `credentialSync.beginLogin/completeLogin`) — its completion now upserts. Slice 3 replaces the entry point, not the flow. Every handler is token-free; pin that with a test like the existing `probe`/`list-keys` one.

**Registry projection.** `ProviderEntry` gains optional `accounts?: { activeId: string | null, perSession: boolean, list: Array<{ id, email?, planType?, accountId? }> }`, set on the shared subscription row from a new `ProviderRegistrySources.chatgptAccounts` source (filled by `listProviderRegistry` from `credentialSync.getStatus()`). `credential` stays `'connected'` when at least one account exists. The row `detail` reads `"2 accounts · daniel@example.com active"` when more than one account exists.

**Manage sheet.** For a shared subscription row, the Credential group becomes an **Accounts** card: one `SettingRow` per account (`as="label"`, radio `leading`, label = email or "Account", description = plan and a shortened workspace id, active row tinted, a danger `Remove` button), a header action `+ Add account` that calls the existing `onAddProvider(entry.id)` path, and below the list a `Per-session accounts` toggle row (description per the mockup; hidden when fewer than two accounts). The existing `Disconnect` moves to the sheet footer as `Disconnect all accounts` with the same confirm. `ProviderList`'s `CredentialChip` for a multi-account row says `N accounts`. Follow ADR-027 testids: `ProviderSheet.account` with `dataId` = account id, `ProviderSheet.accountRemove`, `ProviderSheet.addAccount`, `ProviderSheet.perSession`, `ProviderSheet.disconnect`.

Mobile: the sheet already renders inside the mobile settings view; verify the new rows read at 390px in the component test (no new mobile code expected).

### Guards (each a test that fails before the change)

1. v2 → v3 migration: a v2 chatgpt credential becomes one active account with email/accountId preserved; a v2 API-key custom provider stays under `credentials`.
2. `upsertAccount`: same workspace updates in place and keeps id and active flag; new workspace appends and does not steal active; first account becomes active.
3. `removeAccount` of the active account promotes the newest remaining and feeds it; removing the last removes both engine copies.
4. Two accounts, two expiries: each is refreshed on its own schedule; only the active one is fed; a revoked refresh sets `needsReauth` for that account only.
5. fs-watch adoption updates the active account only.
6. `getStatus`, `provider-account:list` and the registry snapshot contain no `access`/`refresh` strings.
7. Registry: the ChatGPT row carries `accounts` with the right active id and `detail`.
8. ProviderSheet: renders N account rows, radio switch calls `provider-account:switch`, Remove calls remove, toggle calls set-per-session and is hidden with one account.
9. The pinned remote channel set includes the four new channels.

### Slice 2a: inject the vault's ChatGPT token into every Codex process

**Landed 2026-09-13** on `codex-integration` (the commit after `855755af`). Built as specified, with these refinements found in review and in the first real-binary run:

- The hook is opt-in at every composition root (`register-engines.ts`, `CodexAuthProvider`, `model-discovery.ts`, the `crossEngineDispatcher` singleton); a session, service or dispatcher built without one injects nothing and never reads the vault, which keeps the real-binary fixtures hermetic.
- `injectionTokenFor(accountId, refreshMarginMs)`: the inject half uses the 15-minute margin, the refresh half passes 0 so a still-valid cached token answers Codex inside its 10 s deadline.
- `CodexTransportError` carries `nativeMessage` for `rpc-error-*` rejections; only the injection path reads it (the refusal text is the product message). A thrown `inject()` is fatal to the session start, never a fall-through to native auth.
- `probe()` reports a revoked active account as `unauthenticated` + `requiresLogin` (ADR-030), not as a healthy subscription.
- `session:auth-required` is a canonical, ringed domain event (`authRequired` on the session, cleared when a turn runs again) but not yet on the wire; Slice 3 adds the snapshot field with the UI that renders it.
- The generator's schema check unwraps the nullable `anyOf` form `account/rateLimits/read` declares for its params; it still pins the params type by name.
- **The real-binary proof ran on Windows x64** (`src/integration/codex/codex-injection.integration.test.ts`, now gated for macOS arm64 and Windows x64; on Windows the child runs without the seatbelt and the fixture isolates by a replacement environment): injection accepted, `account/read` reports a `chatgpt` account with the fake email, native logins refused with "External auth is active", no `auth.json` written; a scripted 401 produced exactly one `account/chatgptAuthTokens/refresh` carrying the workspace id, the retry carried the rotated token and the turn completed.
- **Findings from that run.** (1) The binary reaches `chatgpt_base_url` (rate limits, `wham/settings/user`) and `GET /v1/models` on its own; the fixture now points `chatgpt_base_url` at itself and answers both 404, because a fake token hitting the real backend earns 401s and unscripted refresh requests. (2) A USER-level `forced_chatgpt_workspace_id` in `config.toml` did **not** gate the injected login on 0.154.0; the test pins the observed behaviour and the refusal path stays wired (unit-tested with a scripted native error). ADR-068 §1's "surfaced verbatim" therefore applies when Codex refuses, which on this binary means a managed `allowed_chatgpt_workspaces` policy.

**Goal.** Every app-server ClaudeUI starts receives the vault's active ChatGPT account through `account/login/start { type: 'chatgptAuthTokens' }` right after `initialize`, answers the app-server's `account/chatgptAuthTokens/refresh` from the vault, attributes the session to the vault account, and drops the native device-code product UI. No per-session pinning yet: the ACTIVE account is what every process gets.

**Read first.** ADR-068 §1 and §4; `docs/protocol-codex/README.md` (regeneration and the real-binary fixture); `src/core/codex/CodexAppServerClient.ts` (`CodexClientOptions.serverMethods`, `onServerRequest` and its `context`), `CodexClient.ts`, `CodexSession.ts` (`start()`, the `serverMethods` const, `requestApproval` dispatch, `this.account`), `CodexService.ts` (`initialize`, `read()`, `accountStatus()`, `startLogin`), `model-discovery.ts`, `src/core/services/cross-engine-dispatcher.ts` (`SpawnCodexTargetFn`, `resolveAndRunCodex`, where the target client is started), `src/core/auth/CodexAuthProvider.ts`, `src/core/ipc/codex-commands.ts`, `src/core/auth/vault/CredentialSync.ts` (Slice 1's per-account runtime, `loadForKey`, `runRefresh`), `scripts/generate-codex-protocol.mjs` (the `methods` / `serverMethods` / `notifications` selection maps), the Codex source at `.cache/codex-src/codex-rs/app-server/src/external_auth.rs` and `request_processors/account_processor.rs` (`login_chatgpt_auth_tokens_response`), `src/integration/codex/` (the real-binary fixture and how it isolates `CODEX_HOME`), `src/renderer/src/components/SettingsDialog/CodexAccount.tsx` and its page entry in `settings-pages.tsx`.

**Design (decided; do not reopen).**

1. _Protocol._ Add to the generator's selection: `serverMethods['account/chatgptAuthTokens/refresh'] = ['ChatgptAuthTokensRefreshParams', 'ChatgptAuthTokensRefreshResponse']`, `methods['account/rateLimits/read'] = ['GetAccountRateLimitsParams', 'GetAccountRateLimitsResponse']`, `notifications['account/rateLimits/updated'] = 'AccountRateLimitsUpdatedNotification'`. Regenerate with `bun run generate-codex-protocol` and confirm `bun run check-codex-protocol` passes; never hand-edit generated files. Windows x64 has the pinned binary vendored.

2. _Token source._ `CredentialSync` gains `async injectionTokenFor(accountId: string | null): Promise<{ accessToken: string; chatgptAccountId: string; chatgptPlanType: string | null; vaultAccountId: string } | null>`. `null` accountId means the active account. Returns null when the vault holds no account for ChatGPT or the account has no workspace id (Codex requires `chatgptAccountId`). If the credential's `expires` is within `REFRESH_MARGIN_MS`, it runs that account's `runRefresh(key)` first (single-flight, per account) and re-reads. It never logs, never appears in `getStatus()`, and is the ONLY method on the class that returns token material; mark it so in its doc comment and add a test that `getStatus()` / `provider-account:list` are unchanged.

3. _Inject after initialize._ `CodexClient.start(params, auth?: CodexAuthHook)` where `CodexAuthHook = { inject(): Promise<InjectionToken | null>; onRefreshRequest(params): Promise<ChatgptAuthTokensRefreshResponse> }`. After the transport handshake, `start` calls `inject()`; when it returns a token it sends `account/login/start { type: 'chatgptAuthTokens', accessToken, chatgptAccountId, chatgptPlanType }` and awaits the response; a rejection is thrown as `CodexInjectionError` carrying the native message verbatim (this is where `forced_chatgpt_workspace_id` surfaces) — no retry, no fallback to native auth. When `inject()` returns null the process is left on whatever Codex's own store holds (a user who never signed in through ClaudeUI keeps working), and the caller records `account = null`. Register `account/chatgptAuthTokens/refresh` in each caller's `serverMethods` and route it to `onRefreshRequest`. The handler answers from `injectionTokenFor(...)` — the app-server sends the WORKSPACE id in `previousAccountId`, so map it back to the vault account whose `accountId` equals it, falling back to the account that was injected into this process, then to active — and must resolve well inside Codex's 10 s deadline: answer from the cached credential unless it is expired. On failure (no account, refresh revoked) reply with a JSON-RPC error and emit `session:auth-required { providerId: 'chatgpt', accountId }` on the session (a new domain event; the renderer wiring is Slice 3, so for now the reducer stores it and the existing `session:error` carries a one-line message "ChatGPT sign-in expired; sign in again from Settings › Models & providers").

4. _Callers._ `CodexSession.start()` (record which vault account id was injected in `this.injectedAccountId`), `CodexService` (its read client; `startLogin` stays as tested code but the provider no longer exposes it), `model-discovery.ts` (through the service), and the dispatch target spawn in `cross-engine-dispatcher.ts` (`SpawnCodexTargetFn` gets the hook; the default spawn uses the active account). One shared hook factory in `src/core/codex/codex-auth-hook.ts` so the four callers cannot drift.

5. _Attribution._ `this.account` becomes `{ engineId: 'codex', vendorId: 'openai', authState: 'authenticated', billingType: 'subscription', label: <email from account/read>, accountId: <vault account id> }` when injected; when not injected it keeps today's derivation from `account/read` and `accountId` is absent. `session:auth-required` is added to the domain-event contract in `src/core/shared/sync/` with a reducer case (store on the session as `authRequired: { providerId, accountId? } | null`, cleared on the next successful turn start).

6. _Provider and UI._ `CodexAuthProvider.probe()` reads the vault's active account first (`credentialSync.getStatus()`): with an account it reports `authenticated` / `subscription` / label = email; without one it falls back to the service's native read as today. `loginStart` / `loginStatus` / `loginCancel` and the channels `codex:login-start`, `codex:login-status`, `codex:login-cancel` are deleted (preload, web adapter, boot-test-app, shared API type, the pinned remote channel set); `codex:auth-status` stays as the availability + model-count query. `CodexAccount.tsx` becomes one `SettingRow`: label "ChatGPT · <email>" with a plan badge (or "Not signed in through ClaudeUI" and, when the native read says a native login exists, the description "Codex is using its own login; sign in here to manage it in ClaudeUI"), description "N accounts available", and a link button "Manage in Models & providers ›" dispatching the existing `open-settings` deep link `{ page: 'models', group: 'providers' }`. The Codex page description loses "No shared-vault credentials are copied."

**Guards.**

1. Transport: `start()` sends `initialize`, then `account/login/start` with exactly the injected triple, and resolves only after the login response; a login rejection surfaces as `CodexInjectionError` with the native message and the process is disposed; `inject() → null` sends no login.
2. Refresh: a server request `account/chatgptAuthTokens/refresh` with `previousAccountId = <workspace>` is answered with that account's token; with an unknown workspace it falls back to the injected account; a revoked account answers an error and the session emits `session:auth-required` and one `session:error`.
3. Expiry: an account within the refresh margin is refreshed once (single-flight) before injection; two concurrent `injectionTokenFor` calls cause one network refresh.
4. `getStatus()` and `provider-account:list` still contain no token material after the new method exists.
5. Attribution: `SessionStatus.account.accountId` equals the vault account id after injection.
6. The pinned remote channel set drops the three login channels and keeps `codex:auth-status`.
7. Component: the new `CodexAccount` row renders the three states and its link dispatches the deep link.
8. Integration (real binary, `src/integration/codex/`, isolated `CODEX_HOME`, fake JWT minted in the test with the claims Codex reads: `exp`, `https://api.openai.com/auth.chatgpt_account_id`, `email`; the fixture's mock provider does not verify signatures): (a) injection accepted, `account/read` reports `chatgpt` with the fake email; (b) the mock provider returns 401 once → the app-server sends `account/chatgptAuthTokens/refresh` with the fake workspace id → the hook answers → the turn completes. Prove that `account/login/start { type: 'chatgpt' }` is refused with "External auth is active" afterwards. Run with `bun run test:integration`.

**Gates.** typecheck, lint, full `bun run test`, `bun run test:integration`, `bun run check-codex-protocol`, prettier on changed files. The reviewer then runs the real app against the owner's account (the ONLY step allowed to touch a real credential, and only the reviewer does it): a Codex session starts under injection, `account/read` shows the ChatGPT email, one short turn completes.

**Out of scope for 2a.** Per-session pinning, `capabilities.auth.perSessionAccount`, the account picker, `codex_session_overrides.accountId`, rate limits and the usage panel, the sign-in dialog, MCP, settings groups.

### Slice 2b: per-session pinning, the picker, rate limits (this kickoff)

**Goal.** A Codex session can pin one stored ChatGPT account (or follow the active one), the pin survives turns, resumes and forks, dispatch targets run under the caller's pin, and the sidebar usage panel shows ChatGPT rate limits per account. Depends on 2a's `CodexAuthHook` / `injectionTokenFor`.

**Read first.** ADR-068 §2; Slice 2a as built (`git log` for its commit and the files it touched); `src/core/codex/settings.ts` (`parseCodexSettings`, `savedCodexOverrides`), `src/core/services/db.ts` (`codex_session_overrides` is a JSON blob in `settings_json` — a new key is NOT a schema migration), `CodexSession.ts` (`setCodexSettings`, `setPermissionMode`'s "applies from the next turn" rule, `start()`), `src/core/providers/ISession.ts`, `src/core/ipc/session.ipc.ts` and `remote-handlers.ts` (`session:set-model` / `session:set-effort` registrations and their `setModel` / `setEffort` helpers), `src/shared/model-capabilities.ts` (`auth: { canDriveLogin, multiAccount }` per engine), `src/renderer/src/components/shared/InlinePickers.tsx` (`EffortPicker` with `nativeOptions`), `src/renderer/src/components/chat/InputBox/InputBox.tsx` and `View.tsx` (how `nativeEffortOptions` flows), `MobileConfigSheet.tsx` (its `Page` union), `src/renderer/src/components/Sidebar/UsagePanel.tsx` (`UsageProgressBar`, `AccountUsage`, `RateWindow`), `src/core/services/usage-fetcher.ts`, the generated `GetAccountRateLimitsResponse` / `RateLimitSnapshot` / `RateLimitWindow` / `AccountRateLimitsUpdatedNotification` types from 2a.

**Design (decided; do not reopen).**

1. _Pin storage._ `CodexSettings` gains `accountId?: string | null` — a string pins a vault account, an explicit `null` clears the pin ("follow active"), absent leaves it alone. `parseCodexSettings` accepts the key (string or null); `savedCodexOverrides` reads a string back. Stored in `codex_session_overrides.settings_json` beside model and effort; no db migration.

2. _Capability._ `EngineCapabilities.auth` gains `perSessionAccount: boolean` — true for Codex, false for the other three. Declared in `model-capabilities.ts` alongside `canDriveLogin` / `multiAccount`.

3. _Command._ `ISession.setAccount?(accountId: string | null): Promise<void>`. New engine-neutral channel `session:set-account` (capability `session-config`, `sessionIdArg: 0`, both transports, added to the pinned remote channel set) that refuses with a clear error when the session's `capabilities.auth.perSessionAccount` is false. `CodexSession.setAccount`: validate the id against `credentialSync.getStatus().accounts` (unknown → error, nothing written); persist via `setCodexSettings({ accountId })`; if the session is idle re-inject NOW with `account/login/start { type: 'chatgptAuthTokens' }` on the live client (allowed while external auth is active — 2a's hook exposes `inject(accountId)`), then re-read `account/read` and update `this.account` + emit status; if a turn is running, store the pending pin and re-inject at the next turn boundary before `turn/start`, mirroring `setPermissionMode`'s next-turn rule. `null` re-injects the active account. The refresh handler from 2a answers for the PINNED account when one is set (its `previousAccountId` mapping already prefers the injected account).

4. _Start, resume, fork._ `start()` reads the saved pin and injects that account; a pinned account that no longer exists injects the active account instead, clears the pin in the overrides, and emits one `session:error` "The pinned ChatGPT account was removed; this session now follows the active account." Forks copy the source's overrides today, so the pin is inherited without new code — pin that with a test.

5. _Dispatch._ `resolveAndRunCodex` passes the CALLER session's `account.accountId` (when the caller is a Codex session with a pin) into `SpawnCodexTargetFn`'s hook so the headless target runs under the same account; callers on other engines or without a pin use the active account.

6. _Picker._ `AccountPicker` in `InlinePickers.tsx`, same visual grammar as `EffortPicker`: trigger shows the pinned account's email (or "Active · <email>" when following), menu lists "Follow active account" first (with the current active email as description) then every stored account (email, plan) with a radio-style check on the current choice, and an "Add account…" item that opens Settings › Models & providers via the `open-settings` deep link. Shown only when `capabilities.auth.perSessionAccount` is true AND the ChatGPT definition's `accounts.perSession` is on AND at least two accounts exist. Data: a store slice `providerAccounts: SharedProviderAccountList | null` loaded from `provider-account:list('chatgpt')` on InputBox mount and re-read after any `provider-account:*` write and after the sign-in flow completes. The current choice comes from a new `SessionStatus.codex.pinnedAccountId: string | null` — it cannot be derived from `account.accountId`, because a session following the active account carries that same id. `MobileConfigSheet` gets an `account` page with the same list. Selecting calls `window.api.setSessionAccount(sessionId, id | null)`.

7. _Rate limits._ Core keeps `ChatgptRateLimits`: `Record<vaultAccountId, { email?: string; planType?: string; primary: RateWindow | null; secondary: RateWindow | null; fetchedAt: number }>`. `RateLimitWindow.usedPercent` maps to `RateWindow.usedPercent`; `resetsAt` is a unix timestamp in SECONDS in Codex's payload (verify against the generated type's doc and the Rust source; convert to ISO 8601 for `RateWindow.resetsAt`). Two sources: (a) on-demand `CodexService.rateLimits(vaultAccountId)` — inject that account into the service's read client, `account/rateLimits/read`, under the service's existing read serialization (one process, sequential re-injection; never a process per account); (b) live sessions forward `account/rateLimits/updated` into the same map under their injected account id. A `config` query `usage:chatgpt-limits` returns the map; a domain event `usage:chatgpt-limits-changed` (no payload) tells clients to re-query. `UsagePanel` gets a "ChatGPT" section: one block per account (email · plan), `UsageProgressBar` for the 5-hour (primary) and weekly (secondary) windows using the existing `getUsageColor` / `formatResetTime`, and the panel's Refresh also triggers the per-account read. Rate limits are read only when the panel is open or refreshed, plus the live pushes; no polling timer.

**Guards.**

1. `parseCodexSettings` accepts `accountId` string and null, rejects other shapes; `savedCodexOverrides` restores the pin.
2. `setAccount` on an idle session re-injects immediately and updates `account.accountId` + `codex.pinnedAccountId`; on a busy session it defers to the next turn start (assert the login is sent before `turn/start`); an unknown id errors and writes nothing; on an engine without the capability the command refuses.
3. Resume with a removed pinned account: active account injected, pin cleared, exactly one `session:error`.
4. Fork inherits the pin (existing override copy).
5. Dispatch: a Codex caller with a pin spawns the target with that account; a Claude caller spawns with active.
6. Picker: hidden when capability false, toggle off, or one account; shows the right current choice; selecting sends `session:set-account` with the id or null; "Add account…" dispatches the deep link. Mobile page renders the same list.
7. Rate limits: `resetsAt` conversion pinned against a known value; per-account read re-injects then reads; a live `account/rateLimits/updated` updates the map under the session's account and fires the change event; the panel renders one block per account with both bars.
8. Integration (real binary, isolated fixture): `setAccount` on a live thread switches `account/read` to the second fake account's email between turns, and a turn completes afterwards.

**Gates.** typecheck, lint, full `bun run test`, `bun run test:integration`, prettier on changed files. Reviewer: real-app drive against the isolated two-account profile — toggle on, picker visible, switch pin, sidebar shows two ChatGPT blocks (fake accounts will show no rate-limit data; the layout and the "unavailable" state are what is checked).
